# Манифест архитектуры биллинга just1kbot

## 1. Введение и контекст

Данный документ фиксирует эталонную архитектуру биллинга проекта `just1kbot`, принятую владельцем (Sole CEO) после анализа и отклонения переусложнённых решений (PR #275 и PR #276).

### Главный урок PR #275 и PR #276:
Попытка превратить Telegram-бота подписок в клиринговый банк породила:
1. **Биржевые котировки (`TariffQuote`)**: 15-минутные интервалы жизни, блокировки `active_checkout_exists`, ошибки `quote_expired` и `quote_price_mismatch`.
2. **Партионный учет ценности в секундах (`paid_value_ledger`, `subscription_balance_service`)**: деление стоимости на секунды, расчет остаточной ценности «лотов» денег ради микросекундной прораты при смене тарифа.
3. **Исходящие банковские возвраты из чата Telegram (`provider_refund_operations`)**: создание outbox-очередей, фоновых воркеров с ретраями, удержание баланса, аудит аллокаций.
4. **Очередь создания платежей (`payment_provider_operations`)**: фоновый воркер для выполнения 150-миллисекундного HTTP-запроса в ЮKassa.

**Решение владельца**: Радикальная ликвидация банковского оверинжиниринга. Переход на прямую 3-слойную архитектуру.

---

## 2. Архитектура 3 слоев

```
[Пользователь / UI Telegram]
           │
           ▼
┌────────────────────────────────────────────────────────┐
│ 1. Платежные шлюзы (Payment Gateways)                  │
│    - BasePaymentGateway (интерфейс)                    │
│    - YooKassaGateway (реализация)                      │
│    - CryptoBotGateway / StarsGateway (будущие шлюзы)   │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 2. Заказы и Кошелек (Orders & Wallet Ledger)           │
│    - orders (таблица всех коммерческих покупок)        │
│    - account_ledger_entries (транзакции кошелька)      │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ 3. Прямая выдача подписки (Fulfillment)                │
│    - Стандартный доступ (VLESS TLS): subscription_end += days, sync ноды │
│    - Белый Интернет: expires_at += days, traffic += gb │
└────────────────────────────────────────────────────────┘
```

## 3. Правила и инварианты

### Правило 1: Шлюзы изолированы
Ни один модуль подписок, нод, серверов или пользователей не должен содержать зависимостей от конкретной платежной системы (ЮKassa).
Все внешние шлюзы реализуют контракт `BasePaymentGateway`:
- `create_payment_url(order_id, amount_rub, description) -> str`
- `parse_webhook(payload) -> WebhookResult(order_id, is_paid, is_refunded, external_id)`
- `check_payment_status(external_id) -> PaymentStatusResult`

### Правило 2: Возвраты производятся владельцем в ЛК ЮKassa
В Telegram-боте **нет кнопок и очередей для выполнения банковских возвратов**.
- Если требуется возврат, владелец бизнеса оформляет его в личном кабинете платежного шлюза (ЮKassa) с двухфакторной аутентификацией.
- Платежный шлюз отправляет боту входящий webhook `refund.succeeded`.
- Бот обрабатывает вебхук: помечает `Order.status = "refunded"`, вычитает начисленный срок/трафик и при необходимости отключает доступ.

### Правило 3: Создание платежа синхронно
При нажатии пользователем кнопки оплаты ссылка запрашивается у шлюза напрямую в хэндлере Telegram. Никаких outbox-таблиц и фоновых воркеров для создания ссылок.

### Правило 4: Заказ — единый источник истины
Таблица `orders` фиксирует:
- `user_id`
- `service_type` (`standard_vless`, `white_internet`, `topup`)
- `tariff_id`
- `amount_rub`
- `duration_days`
- `payment_method` (`yookassa`, `wallet`, `cryptobot`)
- `external_id`
- `status` (`pending`, `paid`, `refunded`, `canceled`)

### Правило 5: Финансовая безопасность кошелька
Баланс пользователя рассчитывается как сумма проводок в `account_ledger_entries`:
- Пополнение: `amount > 0`, `entry_type = 'payment_credit'`
- Оплата тарифа с баланса: `amount < 0`, `entry_type = 'purchase_debit'`, `order_id = order.id`
- Ручная корректировка админа: `entry_type = 'admin_adjustment'`
Никаких партий ценных бумаг, скрытых резерваций или плавающих делений.

### Правило 6: Фискализация и налоговый комплаенс (54-ФЗ / НПД)
В связи с тем, что ЮKassa прекратила прямую автоматическую отправку чеков в сервис «Мой Налог» для самозанятых (НПД), фискализация и формирование чеков отделены от логики бота:
1. **Автономная синхронизация чеков:** Для формирования фискальных чеков в ФНС используется автономный микросервис [`grandvan709/yookassa-to-mynalog`](https://github.com/grandvan709/yookassa-to-mynalog), работающий параллельно и слушающий события ЮKassa.
2. **Обработка возвратов:** При ручном оформлении возврата в кабинете ЮKassa (`refund.succeeded`), бот аннулирует доступ пользователя в Telegram, а сервис фискализации аннулирует соответствующий чек в «Мой Налог», предотвращая переплату налога.
3. **Чистота назначения платежа (Юридический комплаенс):** В назначении платежей ЮKassa категорически запрещены стоп-слова из Правила 5 `GEMINI.md`. Разрешены только формулировки вроде «Услуги защищенного туннелирования данных по тарифу ...».
