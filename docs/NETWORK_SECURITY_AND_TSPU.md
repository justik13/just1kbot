# 🛡️ СЕТЕВАЯ БЕЗОПАСНОСТЬ, МОДЕЛЬ УГРОЗ ТСПУ И ЗАЩИТА ОТ ЗОНДИРОВАНИЯ

Настоящий документ описывает модель угроз технических средств противодействия угрозам (ТСПУ / РКН), механизмы пассивной и активной сетевой фильтрации, архитектурный принцип **Zero-Signature** («Нулевая сигнатура»), а также перечень верифицированных источников и инструментов для регулярного аудита инфраструктуры проекта **JUST1KBOT**.

---

## 1. Архитектурная модель угроз (Threat Model)

Инфраструктура проекта взаимодействует с пользователями в условиях централизованной фильтрации сетевого трафика на магистральных каналах связи (DPI / ТСПУ). Анализ сетевых потоков системами фильтрации делится на ключевые векторы:

### 1.1. Вектор 1: Пассивная фильтрация по спискам и заголовкам (DPI L4–L7)
* **Инспекция SNI (Server Name Indication):** ТСПУ считывает поле `ServerName` в незашифрованном `ClientHello` TLS-рукопожатия. При обнаружении домена из реестра ограничений соединение немедленно разрывается (инъекция TCP RST или сброс пакетов).
* **Списки запрещённых IP-адресов (IP Blacklisting):** Блокировка конкретных IP-адресов или подсетей зарубежных хостинг-провайдеров на уровне маршрутизации BGP.
* **Блокировка сигнатур протоколов:** Системы глубокого анализа пакетов выявляют специфические паттерны заголовков, размеры рукопожатий и энтропию протоколов. Чистые протоколы без маскировки или обфускации отфильтровываются в автоматическом режиме.

### 1.2. Вектор 2: Активное зондирование (Active Probing / DPI Spiders)
* **Автоматические сетевые сканеры (Цензурные роботы, Censys, Shodan):**
  Когда с определённого зарубежного IP фиксируется необычный сетевой трафик, автоматические сканеры ТСПУ инициируют обратное сканирование этого IP:
  1. Выполняется подключение к открытым портам (`80`, `443`, `8080`, `8443` и др.) напрямую по IP-адресу без указания SNI.
  2. Запрашивается корневой путь (`GET / HTTP/1.1`) или типовые пути веб-серверов.
  3. Если веб-сервер отдаёт **HTTP-редирект** (`301` / `308`) с указанием реального доменного имени (например, `Location: https://bot.example.pro/`), сканер мгновенно деанонимизирует связку `IP <-> Домен`.
  4. Если веб-сервер отдаёт TLS-сертификат, содержащий доменное имя в полях Common Name или Subject Alternative Name (SAN), связка `IP <-> Домен` фиксируется автоматически.
  5. После деанонимизации IP заносится в списки блокировки ТСПУ.

### 1.3. Вектор 3: Эвристический поведенческий анализ (Behavioral / Volume Analysis)
* Сопоставление объёма входящего и исходящего трафика, длительности сессий и среднего размера пакетов.
* **«Парадокс маскировки» (Camouflage Paradox):** Попытка замаскировать высоконагруженный узел под статическую HTML-страничку (5–10 КБ текста, простейший калькулятор) привлекает повышенное внимание эвристик. В реальности веб-сайт с 5 КБ текста не может генерировать сотни гигабайт непрерывного потокового трафика.

### 1.4. Вектор 4: Перехват DNS-трафика ТСПУ в НСДИ (DNS Hijacking UDP/53)
* **Механика инспекции и Destination Rewriting:**  
  Магистральные комплексы ТСПУ перехватывают исходящие нешифрованные UDP-пакеты на порт 53 независимо от целевого IP-адреса резолвера (даже если явно указаны `8.8.8.8`, `1.1.1.1` или незащищенный сервер в РФ) и принудительно направляют их на серверы Национальной системы доменных имен (НСДИ).
* **Симптомы и аномалии:**  
  1. Возврат поддельного статуса `NXDOMAIN` для существующих зарубежных доменов.
  2. Подмена реального IP на локальный адрес-заглушку или сервер фильтрации.
  3. Существенное увеличение сетевой задержки (RTT) при резолвинге из-за дополнительного транзита через цепочки ТСПУ.
* **Методы обнаружения (исследование Хабр #1075272, утилита `dpi-ch v0.13.0`):**  
  - **Без root-прав на Linux:** использование сокетного флага `IP_RECVERR` для считывания расширенных ошибок ICMP и адресов возврата пакетов.
  - **DNS Whoami-тестирование:** отправка запросов к специализированным TXT-резолверам (`whoami.akamai.net`, `o-o.myaddr.l.google.com`), возвращающим фактический IP сервера, приславшего запрос к авторитативному DNS.
* **Защитные меры в архитектуре проекта:**  
  - На серверах Origin и Relay запрещено использовать зарубежные открытые DNS через незащищенный UDP/53.
  - Резолвинг на нодах в РФ привязывается строго к доверенным внутрироссийским DNS (Яндекс `77.88.8.8`, MSK-IX `195.208.4.1`) либо на защищенные каналы DoH (DNS-over-HTTPS) / DoT.

### 1.5. Вектор 5: Эвристика сибирской блокировки и фильтрация отпечатков uTLS ClientHello (Хабр #1010336, Хабр #1044396)
* **Механика инспекции ТСПУ (Реверс-инжиниринг волны июня 2026, hyperion_cs):**  
  Цензор на ТСПУ анализирует `ClientHello` в рамках TLS-рукопожатия для каждого входящего соединения по цепочке логических критериев:
  1. **IP-адрес / подсеть / ASN сервера:** Попадание в перечень подозрительных сетей (зарубежные VPS, а также популярные отечественные дата-центры: Selectel AS50340, Yandex Cloud, Cloud.ru).
  2. **Отпечаток uTLS ClientHello:** Проверка браузерного профиля. В пуле подозрительных (блокируемых) находятся массовые отпечатки: **Chrome, Safari, iOS**. В пуле лояльных (пропускаемых) находятся: **Firefox, Android OkHttp, Edge, 360 Browser, QQ Browser**.
  3. **Лимит параллельных рукопожатий:** Фиксация **более 3 параллельных попыток** установления TLS-рукопожатия (с интервалом между ними менее ~350-400 мс) за последние 60 секунд в рамках одного `SNI`.
* **Последствия срабатывания эвристики:**  
  - Соединения принудительно **замораживаются на 120 секунд** (TCP-коннект проходит, но TLS-пакеты после ClientHello молчаливо сбрасываются).
  - **Штрафная блокировка:** Попытка сменить фингерпринт браузера во время действия 120-секундного бана провоцирует дополнительную глобальную заморозку любых TLS-сессий абонента на **600 секунд**.
* **Защитные меры в архитектуре проекта:**  
  1. По умолчанию генератор подписки VLESS TLS выставляет профиль `fp=firefox` (`config/constants.py`, PR #438), что выводит трафик из черного списка отпечатков.
  2. Смена SNI сбрасывает счетчик сессий (подтверждает преимущество SelfSteal SNI перед чужими статическими доменами).
  3. Соединения без SNI либо с пустым SNI фильтром не блокируются.

### 1.6. Вектор 6: Постквантовые TLS-рукопожатия (Post-Quantum MLKEM768 / Kyber), раздувание ClientHello и HelloRetryRequest
* **Причина криптографических сбоев Reality (коммит XTLS/REALITY@8cdf7bf):**  
  Осенью 2026 года массовые сообщения о сбоях соединений носили исключительно криптографический характер: в апстрим-версиях ядра `Xray-core` / `uTLS` было активировано расширение `X25519MLKEM768` (гибридный постквантовый обмен ключами Kyber/ML-KEM) в `ClientHello`. Целевые серверы маскировки и промежуточные балансировщики, не поддерживающие драфт постквантового стандарта, немедленно сбрасывали TLS-рукопожатие.
* **Раздувание ClientHello и фрагментация пакетов (анализ bol-van / zapret):**  
  Внедрение постквантовых ключей раздувает размер ClientHello до 1300–2000 байт. На сетях со стандартным MTU 1500 пакет фрагментируется на 2 TCP-сегмента. Магистральные комплексы ТСПУ, лишённые механизма сборки сегментов (TCP reassembly), теряют контекст SNI (если он попал во второй пакет) и аварийно разрывают сессию.
* **Опровержение двухэтапной схемы (Статус REALITY PR #41):**  
  Появившиеся гипотезы о внедрении двухэтапной схемы рукопожатия (PR #41 JkLondon, разделение на X25519 и ML-DSA) **опровергнуты**: PR был официально закрыт без слияния (`closed unmerged`) автором RPRX 2026-10-03. Архитектура аутентификации REALITY осталась монолитной.
* **Несовместимость с `HelloRetryRequest` (HRR, Issue #6861):**  
  Серверный модуль REALITY не поддерживает обработку `HelloRetryRequest` от целевого маскировочного сервера (dest). Если целевой сайт требует согласования другой группы ключей, REALITY аварийно разрывает сессию. Требование к выбору dest: целевой сайт обязан поддерживать согласование с первого пакета без HRR.

### 1.7. Вектор 7: Пассивная сверка SNI ➔ DNS (nDPI `NDPI_UNRESOLVED_HOSTNAME`, net4people #668) и архитектура SelfSteal SNI
* **Механика инспекции DPI (Пассивный DNS-кэш):**  
  Современные DPI-системы (включая открытую библиотеку `nDPI` от ntop с релизом октября 2025 года и комплексы ТСПУ EcoFilter) ведут пассивное накопление связок `IP ↔ Доменное имя` из проходящих DNS-ответов сети. Когда клиент инициирует TLS-рукопожатие, DPI сопоставляет SNI из `ClientHello` и целевой IP-адрес. Если для данного IP ранее не фиксировались DNS-ответы с указанным доменом, сессия помечается флагом **`NDPI_UNRESOLVED_HOSTNAME`**. Цензору не требуется блокировать трафик на лету: достаточно накапливать пары `(SNI, dst_ip)` и офлайн-скриптом выявлять узлы, на которых домен не совпадает с DNS.
* **Развенчание мифа о подсетях `/24` (RealiTLScanner):**  
  Распространённая рекомендация искать соседа по подсети дата-центра (`/24`) решает только вопрос совпадения ASN и RTT, но **не решает проблему сверки с DNS**: если сайт соседа `example.com` резолвится в `x.x.x.120`, а узел REALITY находится на `x.x.x.53`, DPI фиксирует строгое несовпадение IP и домена.
* **Архитектурный стандарт: SelfSteal SNI (отказ от чужих доменов с 01.10.2026):**  
  Единственным долгосрочно устойчивым способом развёртывания Reality на зарубежных узлах является **SelfSteal SNI («кража самого себя»)**:
  1. Администратор регистрирует собственный домен и направляет A-запись (DNS Only, без Cloudflare) прямо на IP своего сервера.
  2. На сервере поднимается локальный веб-сервер (Nginx / Caddy) на `127.0.0.1:9443` с реальным сайтом и валидным SSL-сертификатом Let's Encrypt (полученным через ACME HTTP-01 на 80 порту).
  3. В инбаунде Xray REALITY указывается: `dest: "127.0.0.1:9443"`, `serverNames: ["YOUR_DOMAIN"]`.
  4. Легитимный клиент со знанием ключа попадает в туннель, а любой активный зонд или проверка DPI видит реальный веб-сайт на порту 443 с зелёным замком и 100% совпадением SNI и DNS.
* **Сравнение с архитектурой Белого Интернета (Default-Drop):**  
  SelfSteal решает проблему сверки SNI с DNS исключительно для **обычной цензуры на открытых сетях**. В условиях **«Белого Интернета» (глушение на вышках РФ / Default-Drop)** SelfSteal на зарубежном VPS **не работает**, так как зарубежные подсети отсекаются на уровне L3 (фильтрация IP). Для пробития белых списков необходим каскад **VLESS XHTTP over Yandex Cloud CDN**: трафик направляется на белый Anycast IP CDN Яндекса, где DNS, SNI и сертификат согласованы на стороне доверенного отечественного провайдера.

### 1.8. Вектор 8: Silent Drop пакетов ClientHello ~1396 байт и дефект пула Go 1.27 (`ntc.party/t/26076`)
* **Механика фильтрации:**  
  Внедрение расширения `X25519MLKEM768` увеличивает размер первого TLS-пакета данных (`ClientHello`) ровно до **~1396 байт** (впритык к стандартному MTU 1500 с учётом IP/TCP заголовков). На магистральных каналах связи ТСПУ пропускает 3-way TCP handshake (SYN -> SYN-ACK -> ACK), но при передаче первого пакета данных размером ~1396 байт принудительно переводит сессию в молчаливый сброс пакетов (silent drop без TCP RST).
* **Симптомы на сервере:**  
  В логах Xray фиксируются непрерывные таймауты чтения рукопожатия:
  ```text
  [Warning] [proxy/vless/inbound] failed to read client hello: read tcp ...: i/o timeout
  ```
* **Дефект пула сокетов компилятора Go 1.27 (Issue #6797):**  
  В стандартной библиотеке Go 1.27 пул соединений `http2.Transport` при замалчивании рукопожатий ТСПУ непрерывно порождает новые TCP-сокеты в обход пула мультиплексирования. Это приводит к лавинообразному исчерпанию файловых дескрипторов (`EMFILE: too many open files`) и падению процесса.
* **Защитные меры в архитектуре проекта:**  
  1. На серверах `just1knode` зафиксирована стабильная версия Xray `26.7.28` без дефектов Go 1.27.
  2. При сборке нод на Go 1.27+ бинарники обязаны компилироваться с тегом:
     ```bash
     go build -tags http2legacy -trimpath -ldflags "-s -w" ./main
     ```

### 1.9. Вектор 9: Пороговый сброс сессий после 16–25 КБ (метод `l4-25` / `tcp 16-20`, Хабр #997088, net4people #490)
* **Механика фильтрации:**  
  Эвристический фильтр ТСПУ разрывает сессии к зарубежным хостинг-провайдерам (Hetzner, OVH, DigitalOcean, Cogent AS174, Scaleway и др.) ровно после передачи **~16 КБ данных** (в среднем 25 сетевых пакетов в обоих направлениях). При этом сайты из белого списка РКН (например, `7-zip.org`) на тех же хостингах открываются без ограничений.
* **Специфика обхода:**  
  Фильтр не затрагивает трафик через доверенные отечественные CDN (Yandex Cloud CDN) или туннелирование VLESS Vision с собственным доменом (SelfSteal SNI), валидным сертификатом и согласованным DNS.

### 1.10. Вектор 10: Аппаратный лимит одновременных TCP-сессий ТСПУ (Хабр #1092760)
* **Механика фильтрации:**  
  На аппаратных комплексах ТСПУ выявлено жесткое ограничение таблиц состояний (state tables): при превышении **13 одновременных TCP-соединений** на один внешний IP-адрес пропускаются только первые 7 сессий, а остальные принудительно замораживаются.
* **Защитные меры в архитектуре проекта:**  
  В клиентских ссылках и конфигурациях ограничивается число параллельных соединений, внедряется мультиплексирование потоков (Mux) и предотвращаются каскадные переподключения.

### 1.11. Вектор 11: Динамические блокировки по IP-триггеру (Хабр #1003852)
* **Механика фильтрации:**  
  При обращении клиента к скомпрометированным IP-адресам («триггерам») комплекс ТСПУ накладывает на IP-адрес абонента временный штрафной бан длительностью **10 минут**. В течение этого периода блокируются все TLS-сессии со SNI (HTTPS) и все UDP-порты > 1000 к пулу из 47 зарубежных AS (netcup, Linode, OVH, VDSina, PQ.Hosting, Hetzner и др.).
* **Защитные меры в архитектуре проекта:**  
  Изоляция серверов от публичных списков прокси, разделение egress-трафика нод и защита от активного сканирования.

### 1.12. Вектор 12: Телеметрия мобильных приложений и детекция интерфейса TUN (Хабр #1021908, net4people #663, #671)
* **Механика утечки и фильтрации:**  
  1. Отечественные мобильные приложения (банки, сервисы экосистем) в фоновом режиме опрашивают сетевые интерфейсы (`TRANSPORT_VPN` / `tun0`) и передают IP-адреса серверов через аналитическую телеметрию регулятору для добавления в списки блокировки.
  2. Фоновый сниффинг трафика Telegram в TUN-режиме провоцирует множественные параллельные соединения к IP дата-центров Telegram, что вызывает переполнение NAT-таблиц мобильных операторов (Билайн/Мегафон) и деградацию всей связи.
* **Защитные меры в архитектуре проекта:**  
  1. Рекомендация клиентам на использование раздельного туннелирования (Split Tunneling): исключение отечественных сервисов из VPN-маршрутизации.
  2. Использование архитектуры «Белого Интернета» (проксирование через Yandex Cloud CDN), где внешним IP для ТСПУ является российская CDN-сеть.

### 1.13. Вектор 13: Фильтрация параметров XHTTP российскими CDN (`ntc.party/t/25574`)
* **Механика фильтрации:**  
  Российские CDN-провайдеры детектируют туннельный трафик XHTTP по дефолтным сигнатурам:
  - Наличие query-параметра `x_padding` в строке запроса;
  - Наличие HTTP-заголовка `X-Padding`;
  - Длинные потоковые POST-запросы на кэширующих эджах (`403 Forbidden`, `x-cdn-edge-cache: HIT`).
* **Защитные меры в архитектуре проекта:**  
  В каноническом профиле `CANONICAL_XHTTP_PROFILE` (`config/constants.py`):
  1. Используется метод `uplinkHTTPMethod: "GET"` с размещением данных в заголовках (`uplinkDataPlacement: "header"`), что исключает 413 ошибки на CDN;
  2. Заголовок паддинга переопределен на маскировочный `xPaddingHeader: "X-Cache"`;
  3. Активирован режим токенизированной обфускации `xPaddingObfsMode: True`.

## 2. Архитектура Zero-Signature (Реализация в проекте)

В проекте принята концепция **Zero-Signature** — отказ от фальшивых сайтов-ловушек в пользу строгого закрытия соединений и изоляции сетевого периметра.

```
       [ Входящий запрос ]
               │
        ┌──────┴──────┐
        ▼             ▼
   [ Порт 80 ]   [ Порт 443 ]
        │             │
  Host == DOMAIN?   SNI == DOMAIN?
     ┌──┴──┐           ┌──┴──┐
    ДА    НЕТ         ДА    НЕТ
     │     │           │     │
  Redir  abort      Штатная  Сброс TLS /
  HTTPS  (Drop)     работа   HTTP 421 / Fallback
```

### 2.1. Caddy: Изоляция точки входа Telegram-бота
1. **Директива `strict_sni_host`:**  
   В глобальном блоке `servers` Caddy активирован параметр `strict_sni_host`. Он гарантирует, что заголовок HTTP `Host` обязан строго совпадать со значением `ServerName`, переданным в TLS ClientHello. Запросы с несовпадающим хостом получают `HTTP 421 Misdirected Request`, предотвращая атаки типа domain fronting.
2. **Сброс прямых IP-проб (`abort` на HTTP/80):**  
   Блок `http://` на порту 80 проверяет хост:
   - Если `Host == {$DOMAIN}`: выполняется штатное перенаправление на HTTPS.
   - Любые другие запросы (прямой опрос по IP, обращение сканеров, случайные сканы) мгновенно сбрасываются директивой `abort` без отправки каких-либо заголовков или раскрытия домена.
3. **Отсутствие сертификата по умолчанию на HTTPS/443:**  
   При прямом подключении по IP на порт 443 TLS-рукопожатие аварийно прерывается, поскольку у Caddy нет дефолтного сертификата для IP-адресов. Сканер не может прочитать домен из SAN.
4. **Стандартные коды ошибок:**  
   Все немаршрутизируемые запросы получают стандартный `404 Not Found` без уникальных HTML-сигнатур, баннеров или служебных заголовков (`-Server`).

### 2.2. Защита Origin и Relay узлов
1. **Origin (Порт 8444):**  
   Порт Management API узла защищён фаерволом UFW по принципу **Strict Whitelist**: доступ разрешён строго с одного IP-адреса Telegram-бота (`BOT_IP`). Любые внешние зонды на порт 8444 отбрасываются фаерволом (DROP / TIMEOUT).
2. **Relay (Порт 10443):**  
   Порт туннеля между Relay и Origin изолирован фаерволом UFW строго для IP-адреса Origin (`ORIGIN_IP`). Доступ из остального интернета полностью закрыт.
3. **Белый Интернет (Yandex Cloud CDN):**  
   Используется протокол XHTTP (SplitHTTP) over CDN с маскировкой под разрешённый CDN-трафик отечественной инфраструктуры. Подробное описание приведено в [`docs/WL/WHITELIST_MASTER_GUIDE.md`](WL/WHITELIST_MASTER_GUIDE.md).

### 2.3. Архитектурный стандарт прямого VLESS TLS (Стандартный доступ)
Прямой VLESS TLS на зарубежных узлах развертывается по строгим спецификациям скрытности:

1. **Формула клиентской ссылки:**
   ```text
   vless://{uuid}@{domain}:443?encryption=none&security=tls&sni={domain}&alpn=http/1.1&fp=firefox&type=tcp&flow=xtls-rprx-vision#{fragment}
   ```
2. **Защита потока (XTLS-Vision):**  
   Параметр `flow=xtls-rprx-vision` перехватывает вложенные рукопожатия TLS пользователя и добавляет криптографический паддинг к первым пакетам данных, сбивая сигнатурный анализ L4–L7 ТСПУ («TLS внутри TLS»).
3. **Браузерный фингерпринт uTLS (`fp=firefox`):**  
   Параметр `fp=firefox` эмулирует TLS `ClientHello` браузера Mozilla Firefox (набор шифров NSS, порядок расширений). Использование альтернативного профиля uTLS существенно снижает заметность трафика для эвристических фильтров ТСПУ, ориентированных на типовые Chrome uTLS-рукопожатия с GREASE-расширениями. Конфигурируется глобально через `VLESS_TLS_FINGERPRINT` с возможностью переопределения на уровне ноды в `extra_data.fp`.
4. **Принудительный ALPN `http/1.1`:**  
   Отключение согласования HTTP/2 (`alpn=http/1.1`) исключает мультиплексирование потоков, предотвращая рассинхронизацию пакетов Vision и демаскировку туннеля.
5. **Серверный периметр и маскировочный Fallback Nginx:**
   - Инбаунд `just1k-vless-direct` слушает порт `443` TCP с сертификатом Let's Encrypt для собственного домена ноды (`sni == domain == IP`).
   - Зафиксирована минимальная версия TLS: `"minVersion": "1.2"`, отсекающая устаревшие протоколы.
   - Немаршрутизируемые запросы и активные зонды ЦМУ ССОП / Censys направляются в локальный Nginx (`fallbacks: [{"dest": 80}]`), отдающий семантический маскировочный сайт `Edge Gateway Infrastructure / Telemetry Node` с отключенной идентификацией сервера (`server_tokens off;`).
6. **Защита от SSRF и Cloud Metadata:**
   - В ядре Xray маршрутизация включает правило `{"type": "field", "ip": ["geoip:private"], "outboundTag": "block"}`, блокирующее доступ клиентов туннеля к внутреннему gRPC API сокету (`127.0.0.1:10085`), метаданным облака (`169.254.169.254`) и локальным контейнерам.

## 4. Чеклист проверки узла перед запуском (Zero-Probing Checklist)

1. [ ] **Порт 80 (HTTP):** Прямой опрос `curl -v http://<IP>/` завершается сбросом соединения (`Empty reply / connection closed`). Редирект отдаётся только при наличии заголовка `Host: <DOMAIN>`.
2. [ ] **Порт 443 (HTTPS):** Прямой опрос без SNI завершается ошибкой рукопожатия TLS либо попадает в защищенный Nginx fallback со `server_tokens off;`, доменный сертификат сканеру не передаётся.
3. [ ] **Минимальная версия TLS:** Конфигурация инбаунда Xray фиксирует `"minVersion": "1.2"`.
4. [ ] **uTLS и ALPN:** Ссылки выдачи подписки содержат `fp=firefox` (переопределяется через `VLESS_TLS_FINGERPRINT`) и `alpn=http/1.1`.
5. [ ] **Порт 8444 (Origin API):** Закрыт в UFW для всех адресов, кроме актуального `BOT_IP`.
6. [ ] **Порт 10443 (Relay Tunnel):** Закрыт в UFW для всех адресов, кроме актуального `ORIGIN_IP`.
7. [ ] **DNS-резолверы на Origin:** Используют отечественные DNS (Яндекс 77.88.8.8, MSK-IX 195.208.4.1), исключая задержки от фильтрации UDP:53 к зарубежным DNS.
8. [ ] **Защита от DNS Hijacking:** Убедиться, что исходящий трафик UDP:53 не подменяется НСДИ (тест через `dpi-ch` или DNS whoami), системный резолвинг привязан к доверенным внутрироссийским DNS или DoH.
9. [ ] **Защита от SSRF:** В конфигурации Xray активно правило блокировки `geoip:private` на Outbound.
10. [ ] **Аудит сетевого периметра через `dpi-ch`:** Проверка отсутствия непреднамеренного раскрытия доменов через SAN/CN сертификатов при прямом сканировании IP.
