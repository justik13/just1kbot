# Coding Agent Rules (Annie)

## 1. Порядок работы

Каждая задача проходит этапы:
`UNDERSTAND → SYNC → INVESTIGATE → PLAN → APPROVE → IMPLEMENT → VERIFY → PR → REPORT`

До явного подтверждения (`APPROVE`) от пользователя код, конфиги и Git не изменяются. Разрешены только read-only действия: чтение файлов, поиск по кодовой базе, `git status`, `git log`, `git diff`.

## 2. Синхронизация и Git

* Перед началом работы проверить текущую ветку (`git branch --show-current`), статус (`git status`) и диф (`git diff`). В репозитории может параллельно работать пользователь или другой агент.
* **Запрещен слепой стейджинг**: команды `git add .`, `git add -A` и `git commit -a` запрещены. Файлы добавляются в коммит строго адресно по конкретным путям: `git add <file1> <file2>`.
* `origin/main` — целевая база для PR. Текущая работа идет в рабочей ветке с учетом реальных файлов на диске (`working tree`).
* Запрещено спорить с пользователем и отрицать локальные файлы. Если пользователь сообщил о правках, проверить диск (`ls / dir`), `git diff` и ветки.

## 2.1. Два репозитория

Проект разделен на два отдельных репозитория:
1. `justik13/just1kbot`: монолит бота, PostgreSQL, Alembic, биллинг, экраны пользователя, админка `/admin`, Docker Compose.
2. `justik13/just1knode`: bash-модули, CLI `just1knode`, сервисы Xray и Amnezia API, Nginx, UFW, gRPC, самодиагностика `just1knode doctor`.
* Смешивать правки между репозиториями запрещено.
* Репозитории связаны через сетевой API ноды (порт 8444). Изменения API ноды обязаны сохранять совместимость с ботом.
* Скрипт `scripts/just1knode.sh` в боте скачивает ветку `main` репозитория ноды. Ломающие изменения в `main` ноды недопустимы.

## 3. Исследование и внешние API

Перед формированием плана изучить связанные файлы, вызовы, конфигурацию и тесты.
* **Память модели не источник истины**: веса содержат устаревшие знания о внешних API (особенно Telegram Bot API, aiogram, Xray, AmneziaWG, ЮKassa).
* Запрещено спорить с пользователем и заявлять «в API этого нет» на основе внутренней памяти. Любое сомнение проверяется по актуальной документации через web search или принимается от пользователя.

## 4. Контекст проекта и принципы анализа

* **Суть**: коммерческий Telegram-сервис сетевых туннелей для клиентов из РФ. Управление единоличное, с перспективой подключения одного администратора поддержки (`ADMIN_IDS`). Админка `/admin` — мобильный пульт управления владельца со смартфона.
* **Масштаб**: целевой ориентир — до 100 пользователей в ближайшее время, до 1 000 в среднесрочной перспективе. Стек монолитный (aiogram, FastAPI, PostgreSQL, Docker Compose), без очередей Kafka/Celery.
* **Качество выше скорости**: анализ должен быть предметным, со ссылками на код `[файл:строки]`.
* Предостережения пользователя — это входящие требования, а не существующие дефекты кода. Не объявлять работающий код сломанным.
* Замечания сторонних моделей (ChatGPT) — это гипотезы (`HYPOTHESIS`), требующие подтверждения кодом.
* **Зеленые тесты не являются доказательством безошибочности**: автотесты проверяют только то, на что написан `assert`. Зеленый статус тестов и проверок CI — это базовый автоматический фильтр явных поломок, а не гарантия идеальной работы в проде. Агент обязан анализировать логику, инварианты и пограничные сценарии независимо от статуса тестов.

## 4.1. Комплаенс и стоп-слова

* **Внешний контур** (экраны бота, чеки, тарифы, уведомления, проверки эквайринга ЮKassa/СБП):
  * Строго запрещены слова: `VPN`, `ВПН`, `обход блокировок`, `белые списки`, `глушилки`, `LTE`.
  * Используется нейтральная лексика: «сетевой доступ», «туннель», «защищенный протокол», «быстрый протокол», «подписка», «узел».
* **Внутренний контур** (код, конфиги Xray/AWG, тесты): используется стандартная техническая терминология без ограничений.

## 4.2. Биллинг

* Бот продает подписки, а не выполняет функции банка или биржи.
* Ссылка на оплату формируется прямым вызовом API шлюза без промежуточных очередей в БД.
* Банковские возвраты выполняет владелец в кабинете шлюза с 2FA. Бот только принимает вебхук `refund.succeeded`.

## 4.3. Сетевые протоколы

* **Стандартный доступ**: только AmneziaWG (`awg`). Клиенты: `AmneziaVPN`, `AmneziaWG`. Обычный WireGuard (`wg`) не поддерживается.
* **Белый Интернет**: только Xray VLESS over XHTTP через Yandex Cloud CDN. Рекомендуемый клиент: `incy`. Формат выдачи: subscription URL (`sub`).
* Контуры AmneziaWG и Xray изолированы в логике бота; серверные узлы могут работать в режимах origin, relay или dual (одновременная работа Xray и AWG на одном сервере).

## 5. План и подтверждение (PLAN & APPROVE)

В плане показать:
1. Что найдено в коде (ссылки на файлы и строки).
2. Что предлагается изменить и почему.
3. Список затрагиваемых файлов.
4. План проверки.

Изменять код разрешено только после явного подтверждения (`APPROVE`) пользователя.

## 6. Реализация и оформление PR

* Работать строго внутри согласованного скоупа.
* Кодировка UTF-8, окончания строк LF, пути со слэшем `/`, код и файлы оборачивать в бэктики `` `code` ``.
* Оформление PR:
  * Первым разделом указывать исходный запрос пользователя (`## Исходная задача / User Request`).
  * Описание передавать через файл: `gh pr create --body-file <file>`, после чего временный файл удалять. Не передавать многострочный Markdown через аргумент `--body "..."`.

## 7. Локальная проверка (LOCAL_VERIFY)

* **На Windows разрешено**: статический анализ (`ruff check`), компиляция (`python -m compileall -q .`), проверка стоп-слов (`pytest tests/test_user_text_audit.py`), быстрые юнит-тесты без БД.
* **На Windows запрещено**: запускать bash-тесты ноды и тяжелые интеграционные сьюты с БД напрямую в ОС.
* Тесты должны адресно защищать систему от регрессий, без дублирования методов-клонов и без задержек `time.sleep`.
* Мусорные dev-файлы удаляются сразу после работы.

## 8. Контроль GitHub Actions CI/CD (AWAIT_CI)

* **Риск-ориентированный регламент**:
  * Для правок кода, логики, БД, платежей или нод: дождаться успешного завершения всех проверок через `gh pr checks <PR> --watch`. Сдавать задачу с упавшим CI запрещено.
  * Для правок пользовательских текстов: обязателен локальный аудит стоп-слов (`pytest tests/test_user_text_audit.py`).
  * Для правок документации, правил и комментариев: блокирующее ожидание CI не требуется при успешном линтере `ruff check`.
* Если проверка упала: посмотреть ошибку через `gh run view <run_id> --log-failed`, исправить, закоммитить и перепроверить.

## 9. Продакшен и правила Git

* Ветка `main` напрямую не меняется, все изменения идут через PR. PR мерджит только владелец.
* Обслуживание на боевых VPS выполняется только через штатные CLI: `just1kbot update` для бота и `just1knode update` для нод.
* Ручные правки файлов, конфигов, ручные `iptables` и перезапуски Docker на проде запрещены (кроме аварийного hotfix с описанием причин).
* Проверки продакшена:
  * **Pre-flight (ДО обновления)**: формируется адресная read-only команда под скоуп текущего PR (psql в контейнер `db` для базы, bash-проверка готовности для ноды). Для правок только текста или документации pre-flight не требуется. Запрещены бессмысленные команды вроде `SELECT count(*)`.
  * **Post-check (ПОСЛЕ обновления)**: на ноде запускается `just1knode doctor`, на боте проверяются контейнеры и логи.

## 10. Итоговый отчёт (REPORT)

В отчёте указать:
* Что изменено (список файлов).
* Результаты локальной проверки.
* Ссылку на PR (для кода — подтвержденный статус проверок CI; для документации/правил — статус локальной проверки без блокирующего ожидания тяжелого CI).
* Адресную команду Pre-flight проверки продакшена (если затронуты БД, биллинг или инфраструктура).
