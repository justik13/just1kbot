# Coding Agent Rules (Annie)

## 1. Регламент работы

Каждая новая задача проходит обязательные этапы:
`UNDERSTAND → SYNC → INVESTIGATE → CLARIFY → PLAN → APPROVE → IMPLEMENT → LOCAL_VERIFY → PUSH/PR → AWAIT_CI → REPORT`

До явного подтверждения (`APPROVE`) от пользователя запрещено менять код, конфиги, структуру проекта и историю Git. Сначала всегда идёт глубокий анализ, даже при прямых командах «сделай», «исправь» или «добавь».

До `APPROVE` разрешены исключительно read-only действия: чтение файлов, поиск по кодовой базе, Git-анализ (`status`, `log`, `diff`), изучение документации и безопасная локальная диагностика.

## 2. SYNC (Рабочий контекст vs Production Baseline)

* Перед началом работы проверить текущую ветку и `git status`.
* **Учёт параллельной работы (Multi-Agent Awareness)**: параллельно в репозитории может работать пользователь или другой агент (например, OpenCode). Перед любыми операциями с ветками и Git агент обязан проверять текущую ветку (`git branch --show-current`), статус (`git status`) и диф (`git diff`), чтобы не перезаписать чужую работу.
* **Категорический запрет на огульный стейджинг (`git add .`, `git add -A`, `git commit -a`)**: добавлять файлы в индекс строго точечно по конкретным именам (`git add <file>`), затрагивая только файлы в скоупе текущей задачи.
* Разделение понятий:
  * `GitHub main` — это стабильная целевая база для PR и релизов на production.
  * **Текущий рабочий контекст (Working Context)** — это текущая ветка и реальные файлы на диске (`working tree`), включая несохранённые/незакоммиченные правки пользователя.
* **Категорический запрет спорить с пользователем и отрицать локальные файлы**: запрещено объявлять файлы «несуществующими» или отказываться от работы только потому, что их нет в `origin/main`. Если пользователь сообщил, что изменил файлы локально или в другой ветке — агент обязан проверить диск (`dir / ls`), незакоммиченный diff (`git diff`), `git status` и ветки репозитория (`git branch -a`, `git log`).
* При необходимости выполнить `git fetch` для обновления `origin/main` и проверки расхождений с целевой веткой.

## 2.1. Архитектура двух репозиториев (Two-Repo Structure)

Проект физически разделён на два независимых репозитория:
1. **Репозиторий Telegram-бота (`justik13/just1kbot`)**: логика бота, PostgreSQL, Alembic, биллинг (ЮKassa, Telegram Stars, CryptoBot), клиентские экраны и админка `/admin`, Docker Compose. Задачи ведутся PR-ами в `justik13/just1kbot`.
2. **Репозиторий узлов (`justik13/just1knode`)**: bash-модули, CLI `just1knode`, Python-микросервисы (`xray-api`, `amnezia-api`), systemd-сервисы, Nginx, UFW, gRPC, системная самодиагностика (`just1knode doctor`). Задачи ведутся PR-ами в `justik13/just1knode`.
* **Изоляция**: категорически запрещено смешивать изменения между репозиториями или коммитить файлы ноды в репозиторий бота (и наоборот).

## 3. INVESTIGATE и актуальные знания

Перед формированием плана изучить:
* Релевантную реализацию, связанные файлы, call sites, конфигурацию, зависимости, историю коммитов и тесты.
* Проектные ресурсы: `docs/main_source.txt`, `docs/WL/`, `docs/amnezia_docs.md`, `docs/projects.txt`.
* **Категорический запрет на спор с пользователем и абсолютный запрет выдавать внутреннюю память модели за источник истины**:
  - Внутренние веса и память модели содержат устаревшие знания о внешних API (особенно Telegram Bot API, aiogram, Xray-core, AmneziaWG, платёжные шлюзы).
  - Категорически запрещено спорить с пользователем и заявлять «в Telegram API этого нет», «это работает иначе» или навязывать устаревшие сигнатуры методов, опираясь на внутреннюю память.
  - Память модели имеет САМЫЙ НИЗКИЙ приоритет. Любое сомнение, параметр или утверждение о внешнем API обязаны проверяться на актуальную дату через официальную документацию (web search / browser) либо приниматься как факт от пользователя. Если пользователь говорит, что API работает так — верить пользователю и проверять свежие доки.
* Неофициальные источники помечать маркером `UNOFFICIAL`.

## 4. Контекст, масштаб и принципы анализа

* **Контекст проекта**: коммерческий Telegram-сервис сетевых туннелей под ключ для реальных клиентов из РФ под единоличным руководством владельца.
* **Масштаб**: текущая цель — до 100 пользователей, среднесрочно — до 1 000 пользователей. Архитектура — надежный монолит (FastAPI + aiogram + PostgreSQL + Docker Compose), без тяжелых очередей (Kafka, Celery).
* **Администрирование**: система ориентирована на владельца, но учитывает поддержку 1-2 доверенных администраторов (`ADMIN_IDS`). Telegram-админка (`/admin`) — полноценный мобильный пульт управления владельца прямо со смартфона.
* **Принцип качества и двойной проверки (Качество > Скорость)**:
  * Скорость генерации ответа или быстрое закрытие задачи не являются метриками успеха. Единственная метрика — надёжность, отсутствие галлюцинаций и нулевой риск для продакшена.
  * Любое утверждение, аргумент функции, зависимость и краевой случай обязаны быть перепроверены по реальному коду и актуальной документации на текущую дату.
  * Запрещено срезать углы, делать поверхностный анализ «для вида» или спешить отчитаться о завершении.
* **Запрет на фетишизацию зелёных тестов (Зелёные тесты ≠ Источник правды)**:
  * Зелёный статус тестов и проверок GitHub Actions CI/CD — это лишь **вспомогательный автоматический фильтр грубых ошибок**, а НЕ источник истины и НЕ доказательство абсолютной работоспособности системы.
  * Автотесты проверяют только то, на что написан конкретный `assert`. Зелёный сьют никогда не гарантирует отсутствие архитектурных дефектов, скрытых регрессий в бизнес-логике, неучтённых краевых случаев (edge cases) или проблем при работе с реальными внешними API, сетью и PostgreSQL.
  * Категорически запрещено делать поверхностные оптимистичные выводы вида «тесты прошли, значит всё гарантированно работает». Агент обязан критически анализировать реальные инварианты, краевые сценарии и логику изменений вне зависимости от статуса автотестов.
* **Запрет на анализ «для галочки» и додумывание «на абум»**: анализ должен быть глубоким, предметным и содержать прямые проверяемые ссылки на код ([файл:строки]).
* **Запрет на «эхо-галлюцинации» и подмену контекста**:
  * Категорически запрещено превращать предостережения или ограничения пользователя («не делай X», «система не знает Y, не выдумывай») в «найденные дефекты существующего кода». Предостережения пользователя — это входящие требования (Constraints), а не существующие баги.
  * Любое заявление о наличии бага, архитектурного дефекта или неэффективности в кодовой базе ОБЯЗАНО иметь проверяемую ссылку на файл и строки ([файл:строки]), где это физически написано. Приписывать коду несуществующие проблемы запрещено.
  * Получив предостережение, агент обязан сначала проверить реальное поведение: если текущий код уже соответствует требованию, зафиксировать это с цитатой кода и не пытаться «чинить» то, что работает правильно.
* **Разделение прямых запросов пользователя и сторонних аудитов (ChatGPT и др.)**:
  - Ответ сторонней нейросети НЕ является источником правды (Single Source of Truth) и НЕ является прямым руководством к действию.
  - Каждое замечание сторонней нейросети обязано адресно проверяться по реальным файлам на диске (`working tree`), кодовой базе и тестам:
    - Если проблема подтверждается кодом — зафиксировать это с цитатой ([файл:строки]) и учесть в плане.
    - Если замечание ошибочно или основано на галлюцинации — аргументированно опровергнуть его с доказательствами из реального кода.
  - Прямые указания пользователя — это требования задачи. Пересылаемый аудит — внешняя гипотеза (`HYPOTHESIS`).
* Обязательно выявлять:
  * Скрытые зависимости, краевые случаи (edge cases) и риски регрессий.
  * Контраргументы к очевидным решениям и возможные побочные эффекты.
  * Альтернативные варианты реализации с оценкой плюсов и минусов.
* Не принимать за пользователя архитектурные, продуктовые или UX-решения. При любых сомнениях или неоднозначностях в требованиях — формулировать чёткие вопросы пользователю.

## 4.1. Архитектурные принципы биллинга и простоты

* **Суть проекта**: бот — это сервис подписок на сетевой доступ для пользователей, а НЕ коммерческий банк и НЕ клиринговая биржа.
* **Принципы простоты и надежности**:
  - **Прямой пайплайн**: генерация ссылки на оплату выполняется напрямую через API платежного шлюза без создания искусственных очередей и outbox-воркеров в БД.
  - **Прозрачный учет и начисление доступа**: понятная и предсказуемая логика добавления доступа пользователю без биржевых котировок, секундных дроблений и скрытых клиринговых списаний (конкретная формула определяется продуктовой логикой тарифа и не сковывается жестким хардкодом в правилах).
  - **Разделение возвратов**: инициация банковских возвратов выполняется владельцем вручную через личный кабинет платежного шлюза (ЮKassa) с 2FA. Бот только принимает входящий вебхук `refund.succeeded` и отключает доступ.
* **Целевая 3-слойная модель биллинга**:
  1. **Платежные шлюзы (Адаптеры)**: изолированные провайдеры (`YooKassa`, `Telegram Stars`, `CryptoBot`) за единым интерфейсом (`create_payment_url`, `parse_webhook`). Замена или добавление шлюза не затрагивает логику подписок.
  2. **Заказы (Orders / Purchases)**: одна понятная запись факта покупки (кто, какой тариф/услугу, сколько рублей, метод оплаты, статус).
  3. **Прямая выдача (Fulfillment)**: подтверждена оплата -> начисление периода доступа -> обновление ключа/конфигурации на сервере.
* **Баланс и безопасность денег**:
  - Деньги пользователей неприкосновенны. Баланс ведется через прозрачные append-only транзакции кошелька (`account_ledger_entries`), исключающие потерю истории и случайные списания. Тарифы имеют фиксированные и прозрачные цены.

## 5. План и подтверждение (PLAN & APPROVE)

В плане показать:
* Что найдено в коде (факты с путями к файлам).
* Что предлагается изменить и почему.
* Список затрагиваемых файлов.
* Выбранный подход и альтернативы.
* План локальной проверки и план контроля CI/CD.

Изменять код строго после явного подтверждения (`APPROVE`) пользователя.

## 6. Факты и доказательства (Evidence)

Использовать разметку:
* `FACT`: подтверждено проверяемым источником (код, Git, диск, установленный пакет, runtime-проверка, официальная документация).
* `INFERENCE`: логический вывод из подтверждённых фактов.
* `HYPOTHESIS`: внешняя гипотеза или сторонний аудит (ChatGPT, Claude и др.), требующий подтверждения кодом.
* `UNKNOWN`: факт установить не удалось.

Не выдумывать имена файлов, функции, API, коммиты или причины поведения. Не называть непроверенное проверенным.

## 7. Реализация (IMPLEMENT)

После `APPROVE` работать автономно внутри согласованного скоупа:
* Держаться строго в рамках плана, без оверинжиниринга и без чрезмерного упрощения.
* Основная рабочая среда: Antigravity 2 (Gemini), вспомогательная: OpenCode.
* Для работы с GitHub использовать `gh` CLI и GitHub MCP. Для актуализации данных использовать browser и `chrome-devtools`.
* **Правила оформления и создания PR на GitHub**:
  * **Обязательная фиксация задачи пользователя**: первым разделом в описании PR обязательно указывать исходный запрос пользователя (`## Исходная задача / User Request`), чтобы ревьюер сразу видел контекст, цели и первоначальные требования.
  * Описание PR передавать СТРОГО через файл: `gh pr create --body-file <file>` (или `gh pr edit --body-file <file>`), после чего временный файл удалять.
  * Категорически запрещено передавать Markdown через аргумент `--body "..."` в PowerShell/Bash (оболочка неизбежно ломает экранирование, кавычки и превращает пути в битые escape-символы).
  * Пути к файлам указывать строго через прямой UNIX-слеш (`/`). Запрещено использовать обратные слеши (`\`), вызывающие повреждение текста (`\b` -> backspace, `\n` -> newline, `\t` -> tab, `\a` -> bell, `\f` -> form feed).
  * Имена файлов, идентификаторы и код в Markdown оборачивать строго в бэктики (`` `code` ``), а НЕ в обратные слеши (`\code\`).

## 8. Локальная проверка (LOCAL_VERIFY)

* **Прагматичный контроль тестов (Risk-Based Verification)**:
  - **HIGH / MEDIUM (логика, код, БД, платежи, инфраструктура ноды, API)**: полный обязательный прогон тестов. Запрещено сдавать задачу без успешных тестов. При этом зелёный статус — это лишь дополнительный фильтр, не отменяющий глубокого анализа логики.
  - **LOW — Пользовательские тексты и экраны бота**: если PR меняет только тексты UI, кнопки или сообщения для клиентов, обязателен только быстрый локальный аудит стоп-слов (`pytest tests/test_user_text_audit.py`). Гонять тяжёлые сьюты ради текста опечатки не требуется.
  - **DOCS / CHORE (документация, README, правила, комментарии, форматирование)**: достаточно проверки компиляции / линтера (`ruff check` / `python -m compileall`). Запуск тяжелых интеграционных тестов для таких правок избыточен.
* **Эффективность тестов и защита от регрессий (Anti-Bloat & Regression Shield)**:
  - **Диагностичность и контракты превыше компактности**: тест обязан адресно защищать систему от реальных регрессий (Regression Shield). Падение теста должно давать мгновенно понятную причину: один сломанный контракт — один упавший `assert` с однозначным контекстом. Запрещено жертвовать диагностичностью или полнотой проверок (`assert_not_called`, `assert_awaited_once`) ради формального сокращения строк.
  - **Без дублирования и искусственного раздувания**: не плодить избыточные методы-копии на тривиальные вариации входных данных; группировать родственные проверки без потери информативности.
  - **Быстродействие и отсутствие задержек**: запрещены реальные задержки (`time.sleep`, долгие `asyncio.sleep`). Предпочитать быстрые изолированные юнит-тесты без БД и bash-подпроцессов там, где проверяется чистая бизнес-логика.
* **Среда Windows**:
  * Разрешено и обязательно: статический анализ (`ruff check`), компиляция (`python -m compileall -q .`), проверка стоп-слов (`pytest tests/test_user_text_audit.py`), быстрые изолированные модульные юнит-тесты без БД, без фоновых процессов и без запуска bash-скриптов (`pytest tests/test_<module>.py`).
  * Запрещено: запускать тесты bash-скриптов (включая тесты нод, перенесённые в репозиторий `just1knode`), тяжёлые сьюты, параллельные тесты и фоновые процессы напрямую в Windows (вызывает зависание подпроцессов, утечки памяти и сбои системы).
  * Системные проверки, тесты bash-скриптов нод и интеграционные проверки запускать в Ubuntu 24.04 через Docker Desktop или делегировать в GitHub Actions CI/CD (`test-node`, `test`, `docker-smoke-test`).
* Удалять за собой временные и отладочные dev-файлы (скрипты, дампы, выгрузки, логи), оставляя working tree чистым.
* Проверять итоговый `git diff`.

## 9. Мониторинг GitHub Actions CI/CD (AWAIT_CI)

* **Дифференцированный контроль CI/CD**:
  - Для задач с изменением кода, логики, БД, платежей или нод: дождаться полного завершения всех проверок через `gh pr checks <PR> --watch` или `gh run watch`. Красный CI/CD = задача НЕ выполнена.
  - Для чисто текстовых правок, комментариев или документации: блокирующее ожидание тяжелых очередей CI не требуется, если пройдены линтеры и аудит стоп-слов.
* **Операционный протокол контроля**:
  1. Запустить мониторинг проверок: `gh pr checks <PR> --watch` или отслеживать через `gh run list --branch <branch>` / `gh run watch <run_id>`.
  2. Если любая проверка упала — немедленно выяснить причину через `gh run view <run_id> --log-failed`.
  3. Устранить ошибку (рассинхрон lockfile, линтер, сломанный тест, миграция), закоммитить, запушить и снова ожидать завершения воркфлоу.
  4. Финальный отчёт разрешено формировать **только после подтверждённого статуса всех проверок: PASS (зелёный чек)**.

## 10. Ограничения Git и продакшен

* Ветка `main` напрямую не изменяется. Все изменения идут через PR.
* PR создаётся из рабочей ветки. Мерджит исключительно пользователь.
* Запрещены merge, force-push и деструктивные команды Git без прямого указания пользователя.
* **Категорический запрет на огульный стейджинг (`git add .`, `git add -A`, `git commit -a`)**: добавлять файлы в коммит строго адресно по конкретным путям (`git add <file>`), чтобы не захватить посторонние изменения или временные файлы.
* **Штатное обслуживание и обновления — строго через CLI (`just1kbot` / `just1knode`)**:
  - Все регламентные действия, обслуживание и обновления на продакшене происходят **исключительно** через штатные утилиты: `just1kbot` (для бота) и `just1knode` (для нод).
  - Все обновления накатываются исключительно через штатные команды: `just1kbot update` для бота и `just1knode update` для нод.
  - Категорически запрещены ручные низкоуровневые команды (ручная правка файлов, конфигов, ручные `iptables`/`sysctl`/`docker` в обход CLI) при штатном обслуживании и релизах.
  - **Исключение — аварийные ситуации (Hotfix & Rollback)**:
    - Ручные команды на продакшене допускаются **только и исключительно** в случаях, если что-то сломалось и требуется экстренный hotfix для быстрого восстановления продакшена, либо для аварийного отката (rollback).
    - При возникновении такой ситуации агент обязан предельно чётко и прозрачно пояснить:
      1. Какую конкретно проблему мы решаем.
      2. Что именно делает предлагаемая команда и почему необходима именно она.
      3. Ожидаемый результат и как проверить успешность выполнения.
* **Безопасность продакшена и стандарт проверок (Pre-flight и Post-check)**:
  - Прод работает на изолированных удалённых VPS. Прямого доступа у агента нет. Владелец выполняет команды вручную. Деструктивные команды на проде категорически запрещены.
  - **Pre-flight проверка (ДО обновления)**:
    - Выполняется строго **до** запуска команд обновления.
    - Агент обязан подготовить адресную read-only команду под конкретный скоуп текущей задачи:
      - Если PR затрагивает базу данных, миграции, финансовые балансы или заказы — готовится **одна цельная, автономная read-only команда psql** в контейнер `db` (`docker compose exec -T db psql -U just1kbot -d just1kbot_bot -x -c "..."`), проверяющая только те таблицы и инварианты, которые меняются в PR (с понятным вердиктом `OK` / `FAIL`). Запрещено проверять `webhook_inbox.status = 'pending'`, так как воркер удален в PR #277 и этот статус копится штатно.
      - Если PR меняет системные настройки, ядро, сеть, фаервол или службы ноды/сервера — готовится **одна цельная, автономная bash-команда** для целевого сервера/ноды, проверяющая текущий runtime, конфигурационные файлы и готовность к накату изменений с однозначным выводом `OK` / `FAIL`.
      - Если PR меняет только код/скрипты без риска для сохранности данных и обновление штатно накатывается через `just1kbot update` / `just1knode update`, либо меняет только тексты, линтеры или тесты — генерировать избыточные pre-flight команды не нужно.
  - **Штатное обновление**: накатывается исключительно через штатные команды: `just1kbot update` для бота и `just1knode update` для нод.
  - **Post-check проверка (ПОСЛЕ обновления)**:
    - Для нод: запуск обновлённого штатного инструмента **`just1knode doctor`** для комплексного подтверждения здоровья служб, gRPC-сокетов, сертификатов и фаервола + адресная проверка внесенного новшества (если требуется).
    - Для бота: проверка статуса контейнеров (`docker compose ps`) и логов, либо адресный post-check.
  - **Запрет на команды «для галочки» и метрики тщеславия**: категорически запрещено давать бессмысленные выборки (`SELECT count(*)`) или проверки вне контекста. Проверка обязана адресно тестировать гипотезу отказа (Failure Mode) текущего изменения.

## 11. Эскалация

Остановиться и спросить пользователя, если:
* Не хватает данных для безопасного решения.
* Есть существенная развилка подходов.
* Требуется бизнес-, продуктовое или архитектурное решение.
* Обнаружен конфликт требований или текущий план больше не подходит.

## 12. Итоговый отчёт (REPORT)

Итоговый отчёт предоставляется только после успешного завершения `LOCAL_VERIFY` и `AWAIT_CI`.
В отчёте обязательно указать:
* Что изменено (список файлов).
* Результаты локальных тестов.
* Результаты проверок GitHub Actions (ссылки и ID успешных запусков `tests`, `Docker Compose CI`).
* Оставшиеся риски и рекомендации.
* Готовая адресная read-only команда Pre-flight диагностики продакшена (строго по контексту задачи ДО обновления, без бессмысленных команд «для галочки»).
