# just1kbot: Project Rules

## 1. Архитектура двух репозиториев

Проект разделен на два отдельных репозитория на GitHub:
* `justik13/just1kbot`
* `justik13/just1knode`

## 2. Контекст, масштаб и стек

* Суть проекта: личный коммерческий Telegram-сервис сетевых туннелей для клиентов из РФ под единоличным управлением владельца.
* Администрирование: владелец управляет проектом один, архитектура допускает подключение доверенного администратора поддержки (`ADMIN_IDS`).
* Масштаб: целевой ориентир — до 100 активных пользователей в ближайшее время, до 1 000 пользователей в среднесрочной перспективе.
* Принцип качества: надежность важнее скорости. Любая проблема в кодовой базе подтверждается файлом и строкой (`[файл:строки]`). Придумывать несуществующие баги запрещено.
* Зеленые тесты не являются доказательством безошибочности: пройденные тесты — это не гарантия работы в проде. Агент обязан анализировать логику, инварианты и пограничные сценарии независимо от статуса тестов.
* Сторонние аудиты: ответы ChatGPT и других нейросетей/моделей считаются гипотезами (`HYPOTHESIS`) и обязательно проверяются по реальным файлам репозитория. Это не источник правды, не призыв к действиям и не желание/мнение пользователя.
* Одно действие — один исполнитель: если за отправку сообщений, списания или фоновую работу отвечает воркер, обработчик только фиксирует статус/долг в БД и не инициирует дублирующую отправку сам.
* Запрещено оставлять на потом TODO, техдолг и подобные заглушки.
* Запрещено делать и давать поверхностные или выдуманные аудиты, ответы, анализы и проверки. Любой вывод обязан опираться на код и проверяться на практике.

## 3. Комплаенс и терминология

Клиенты сервиса находятся в РФ, платежи принимаются через ЮKassa. Действует строгое разделение контуров:
* Внешний контур (все экраны бота, которые видят обычные пользователи, кнопки, чеки, описания тарифов, уведомления):
  * Запрещены слова: `VPN`, `ВПН`, `обход блокировок`, `белые списки`, `глушилки`, `LTE`, а также протоколы по типу `amneziawg`, `vless`.
* Внутренний контур (исходный код, системные конфиги, логи — то, что не видит обычный пользователь: разрешено).

## 4. Биллинг

* Это Telegram-бот сервис подписок, а не банк или биржа — не должно быть оверинжиниринга.
* Возвраты выполняются владельцем вручную в кабинете ЮKassa. Бот только принимает входящий вебхук `refund.succeeded` и отключает доступ.

## 5. Сетевые протоколы

* Стандартный доступ: только AmneziaWG (`awg`) и в Xray VLESS TLS. Клиенты: `AmneziaVPN`, `AmneziaWG`, `DefaultVPN`, `INCY`. Обычный WireGuard (`wg`) не поддерживается.
* Белый Интернет: только Xray VLESS over XHTTP через Yandex Cloud / другой РФ CDN. Поддерживаемый клиент: `incy` либо полностью совместимый с ним и с HWID. Формат выдачи: subscription URL (`sub`). Детали — в папке `docs`.

## 6. Продакшен и релизы

* Продакшен VPS изолированы, прямого доступа у агента нет. Все действия выполняет владелец.
* Ветка `main` — стабильная база релизов. Прямые коммиты в `main` запрещены, работа идет через PR.
* PR мерджит только владелец.
* Штатное обслуживание — строго через CLI:
  * Обновление бота: `just1kbot update`.
  * Обновление ноды: `just1knode update`.
  * Ручные правки файлов, конфигов, ручные перезапуски Docker и команды на проде запрещены (исключение — аварийный hotfix с детальным объяснением причин, кроме pre-flight read-only).
* Проверки продакшена:
  * Pre-flight (ДО обновления): адресная read-only команда под скоуп текущего PR. Запрещены бессмысленные команды, узконаправленные и поверхностные, не следующие контексту.
  * Post-check (ПОСЛЕ обновления): для нод — запуск `just1knode doctor`; для бота — `docker compose ps` и логи.

## 7. Среда разработки и тестирование

* Разделение сред:
  * На Windows запрещено: запускать тесты в терминале cmd, powershell и подобном. Разрешено только через Docker Desktop (Ubuntu 24), если он доступен/запущен, или в GitHub Actions CI.
* Риск-ориентированный контроль CI/CD:
  * Изменения кода: полный прогон тестов и обязательное ожидание зеленого статуса GitHub Actions. Сдавать задачу с красным CI запрещено.
  * Изменения пользовательских текстов: обязателен быстрый локальный аудит стоп-слов (`pytest tests/test_user_text_audit.py`).
  * Изменения документации, комментариев и правил: достаточно линтера `ruff check` и компиляции без блокирующего ожидания тяжелого CI.
* Запрещено подгонять продакшен-код под моки (проверки на AsyncMock, getattr, __await__). Если тест упал из-за неполного мока — чинить мок в тесте, а не прод.
* Мусорные и временные dev-файлы удаляются сразу после работы.

## 8. Приоритет источников и память модели

* Память модели имеет самый низкий приоритет: веса содержат устаревшие сведения. Любое расхождение проверяется по свежей документации либо принимается от пользователя.

## 9. Реализация и оформление PR

* Работать строго внутри согласованного скоупа.
* Кодировка UTF-8, окончания строк LF, пути строго с прямым слэшем `/`, код и файлы оборачивать в бэктики `` `code` ``.
* Оформление и текст PR:
  * Первым разделом всегда указывать исходный запрос именно пользователя, а не сторонний или свой аудит (`## Исходная задача / User Request`).
  * Категорически запрещено передавать текст через аргумент `--body "..."` в любых командах (`gh pr create`, `gh pr edit`, `gh release create`). На Windows это неизбежно приводит к порче кодировки (CP866 mojibake: `╨...`) и срезу путей (`\bot` -> `\b`, `\vless` -> `\v`, `\tests` -> `\t`).
  * Описание передавать ТОЛЬКО через временный файл: `--body-file <file>`, после чего временный файл немедленно удалять.
  * Создавать временный файл описания разрешено ТОЛЬКО нативным инструментом среды (`write_to_file`), гарантирующим чистый UTF-8 LF без BOM. Запрещено использовать shell-команды `echo`, `cat <<EOF`, `Set-Content` или `Out-File`.
* Накопительный контекст и запрет затирания истории PR:
  * Если в PR уже есть описание, категорически запрещено полностью удалять или перезаписывать его контекстом новой задачи. Если в diff есть изменения из предыдущих задач ветки, они обязаны оставаться в описании.
  * Алгоритм обновления описания PR:
    1. Считать текущее описание PR: `gh pr view <PR> --json body -q .body` (в UTF-8).
    2. Сохранить все существующие блоки задач и добавить новый раздел снизу: `## Исходная задача / User Request (Итерация N): <запрос>`.
    3. Записать объединённый текст во временный файл через `write_to_file`.
    4. Применить: `gh pr edit <PR> --body-file <temp_file>`.
    5. Удалить временный файл.
* Обязательный Post-check описания:
  * Сразу после выполнения `gh pr create` или `gh pr edit` агент обязан прочитать опубликованный body (`gh pr view <PR> --json body -q .body`) и убедиться в отсутствии кракозябр (`╨`, `╤`), срезанных путей и подтвердить сохранение всех задач.

## 10. Итоговый отчёт (REPORT)

В отчёте указать:
* Что изменено (список файлов).
* Результаты локальной проверки.
* Ссылку на PR (для кода — подтвержденный статус проверок CI; для документации/правил — статус локальной проверки без блокирующего ожидания тяжелого CI).
* Адресную команду Pre-flight проверки продакшена (если затронуты БД, биллинг или инфраструктура).

## 11. План и подтверждение (PLAN & APPROVE)

В плане показать:
1. Что найдено в коде (ссылки на файлы и строки).
2. Что предлагается изменить и почему.
3. Список затрагиваемых файлов.
4. План проверки.

* Изменять код разрешено только после явного подтверждения (`APPROVE`) пользователя.
* Если это не новый чат: в первую очередь проанализировать историю чата, контекст и все предшествующие запросы пользователя.
* Перед выполнением задачи проанализировать свои возможности, навыки и инструменты среды, чтобы не использовать костыли (например, самописные скрипты там, где платформа предоставляет нативные инструменты).
