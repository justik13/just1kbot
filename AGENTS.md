# just1kbot: Project Rules

## Production и Git

* GitHub `main`: стабильная production-база (Production Baseline) и эталон релизов.
* Продакшен изолирован: ветка `main` развёрнута на удалённых production VPS и обслуживает реальных пользователей. Прямого доступа (SSH/сеть) к production-инфраструктуре у агента нет.
* Production обновляется владельцем вручную через `just1kbot` для бота и `just1knode` для нод.
* **Штатное обслуживание и обновления — строго через CLI (`just1kbot` / `just1knode`)**:
  - Все регламентные действия, обслуживание и обновления на продакшене происходят **исключительно** через штатные утилиты: `just1kbot` (для бота) и `just1knode` (для нод).
  - Все обновления накатываются исключительно через штатные команды: `just1kbot update` для бота и `just1knode update` для нод.
  - Категорически запрещены ручные низкоуровневые команды (ручная правка файлов, правка конфигов, ручные `iptables`/`sysctl`/`docker` в обход CLI) при штатном обслуживании и релизах.
  - **Исключение — аварийные ситуации (Hotfix & Rollback)**:
    - Ручные команды на продакшене допускаются **только и исключительно** в случаях, если что-то сломалось и требуется экстренный hotfix для быстрого восстановления продакшена, либо для аварийного отката (rollback).
    - При возникновении такой ситуации агент обязан предельно чётко и прозрачно пояснить:
      1. Какую конкретно проблему мы решаем.
      2. Что именно делает предлагаемая команда и почему необходима именно она.
      3. Ожидаемый результат и как проверить успешность выполнения.
* Любое изменение, попадающее в `main`, должно быть проверено, соответствовать требованиям проекта и быть готово к безопасному production deployment без риска сбоев.
* **Стандарт проверки продакшена (Pre-flight и Post-check)**:
  - Продакшен полностью изолирован, любые команды владелец выполняет вручную. Деструктивные команды на проде категорически запрещены.
  - **Pre-flight проверка (ДО обновления)**:
    - Выполняется строго **до** запуска команд обновления.
    - Агент обязан подготовить адресную read-only команду под конкретный скоуп текущей задачи:
      - Если PR затрагивает базу данных, миграции, финансовые балансы или заказы — готовится **одна цельная, автономная read-only команда psql** в контейнер `db` (`docker compose exec -T db psql -U just1kbot -d just1kbot_bot -x -c "..."`), проверяющая только те таблицы и инварианты, которые меняются в PR (с понятным вердиктом `OK` / `FAIL`). Запрещено проверять `webhook_inbox.status = 'pending'`, так как воркер удален в PR #277 и этот статус копится штатно.
      - Если PR меняет системные настройки, ядро, сеть, фаервол или службы ноды/сервера — готовится **одна цельная, автономная bash-команда** для целевого сервера/ноды, проверяющая текущий runtime, конфигурационные файлы и готовность к накату изменений с однозначным выводом `OK` / `FAIL`.
      - Если PR меняет только код/скрипты без риска для сохранности данных и обновление штатно накатывается через `just1kbot update` / `just1knode update`, либо меняет только тексты, линтеры или тесты — генерировать избыточные pre-flight команды не нужно.
  - **Штатное обновление**: накатывается исключительно через штатные команды: `just1kbot update` для бота и `just1knode update` для нод.
  - **Post-check проверка (ПОСЛЕ обновления)**:
    - Для нод: запуск обновлённого штатного инструмента **`just1knode doctor`** для комплексного подтверждения здоровья служб, gRPC-сокетов, сертификатов и фаервола + адресная проверка внесенного новшества (если требуется).
    - Для бота: проверка статуса контейнеров (`docker compose ps`) и логов, либо адресный post-check.
  - **Запрет на команды «для галочки» и метрики тщеславия**: категорически запрещено давать бессмысленные выборки (`SELECT count(*)`) или проверки вне контекста. Проверка обязана адресно тестировать гипотезу отказа (Failure Mode) текущего изменения.
* `main` напрямую не изменяется. Все изменения проходят через PR.
* PR мерджит только владелец проекта. Агенту мерджить запрещено.
* Разделение Production Baseline и Рабочего контекста: `origin/main` — это целевая база для PR. Текущая работа ведётся в локальной рабочей ветке (`HEAD`) и с реальным состоянием файлов на диске (`working tree`), включая несохранённые/незакоммиченные правки пользователя. Запрещено игнорировать локальные файлы пользователя или спорить о том, что их «нет в main». Если пользователь сообщил, что изменил файлы локально или в другой ветке — агент обязан проверить диск и ветки репозитория.
* **Учёт параллельной работы и запрет на огульный стейджинг (Multi-Agent Awareness & Selective Staging)**:
  - В репозитории параллельно может работать пользователь или другой агент (например, OpenCode).
  - Перед любыми операциями с Git агент обязан проверять текущую ветку (`git branch --show-current`), статус (`git status`) и диф (`git diff`), чтобы случайно не затереть и не перехватить чужие правки.
  - **Категорический запрет на слепой стейджинг (`git add .`, `git add -A`, `git commit -a`)**: добавление файлов в индекс производится **СТРОГО адресно по конкретным путям** (`git add <file1> <file2>`). В коммит разрешено включать только те файлы, которые относятся к текущей согласованной задаче. Это исключает случайный захват временных файлов, конфигов, секретов или параллельных изменений пользователя/другого агента.

## Архитектура двух репозиториев (Two-Repo Structure)

Проект физически разделен на два независимых репозитория на GitHub со своими ветками, PR, тестами и версионированием:
1. **Репозиторий Telegram-бота (`justik13/just1kbot`)**:
   - Назначение: монолит бота, база данных (PostgreSQL, SQLAlchemy, Alembic), биллинг и эквайринг (ЮKassa, Telegram Stars, CryptoBot), интерфейс пользователя и админ-панель (`/admin`), Docker Compose.
   - Задачи, связанные с логикой бота, БД, тарифами или Telegram UI, ведутся СТРОГО в этом репозитории с созданием PR в `justik13/just1kbot`.
2. **Репозиторий серверных узлов (`justik13/just1knode`)**:
   - Назначение: управление и инфраструктура серверов — утилита CLI `just1knode`, модули настройки Origin/Relay/Dual, Python-микросервисы (`xray-api`, `amnezia-api`), шаблоны Nginx, UFW, gRPC, системная самодиагностика (`just1knode doctor`).
   - Задачи, связанные со скриптами ноды, конфигурацией ядер, Nginx или фаерволом, ведутся СТРОГО в этом репозитории с созданием PR в `justik13/just1knode`.
* **Правило изоляции**: категорически запрещено смешивать изменения между репозиториями, пытаться коммитить файлы ноды в репозиторий бота или наоборот. Каждый репозиторий автономен.

## Контекст проекта, масштаб и архитектура

* **Суть проекта**: коммерческий Telegram-сервис сетевых туннелей под ключ для реальных клиентов, спроектированный под единое руководство владельца.
* **Целевая аудитория**: клиенты **исключительно из РФ**. Это обуславливает жесткие требования к финансовому комплаенсу (ЮKassa / СБП) и необходимость надежного контура Белого Интернета (Xray VLESS over XHTTP через Yandex Cloud CDN) наряду со стандартным AmneziaWG.
* **Целевой масштаб**:
  - Ближайший ориентир: **до 100 активных пользователей**.
  - Среднесрочный потолок: **до 1 000 активных пользователей** (дальнейшее расширение оценивается по мере роста).
  - Архитектурное решение: надежный монолитный стек (PostgreSQL, aiogram 3, FastAPI, Docker Compose) полностью покрывает данный масштаб с большим запасом по производительности. Использование тяжелых распределенных очередей (Celery, Kafka) избыточно.
* **Команда и администрирование**:
  - Управление проектом единоличное, но система предусматривает поддержку 1-2 доверенных администраторов (`ADMIN_IDS`) для клиентской техподдержки при росте базы.
  - Административный интерфейс в Telegram (`/admin`) является основным мобильным пультом владельца для оперативной поддержки пользователей, управления серверами и контроля статистики прямо со смартфона.
* **Принцип качества и двойной проверки (Качество > Скорость)**: Лучше сделать глубокую двойную работу и перепроверить реализацию дважды, чем сделать поверхностно и быстро ради галочки. Скорость не является приоритетом. Любое утверждение, зависимость и краевой случай должны быть перепроверены по реальному коду и актуальным источникам. Запрещено срезать углы ради быстрого отчёта.
* **Запрет на фетишизацию зелёных тестов (Зелёные тесты ≠ Источник правды)**:
  - Зелёный статус локальных тестов и проверок GitHub Actions CI/CD — это лишь **вспомогательный автоматический фильтр грубых ошибок**, а НЕ доказательство абсолютной работоспособности системы.
  - Автотесты проверяют строго то, на что написан конкретный `assert`. Зелёный сьют не гарантирует отсутствие архитектурных просчетов, скрытых регрессий в бизнес-логике, необработанных краевых случаев (edge cases) или проблем при работе с реальными внешними API, сетью и PostgreSQL.
  - Категорически запрещено делать поверхностные оптимистичные выводы вида «тесты прошли, значит всё гарантированно работает». Агент обязан критически анализировать реальные инварианты, краевые сценарии и логику изменений вне зависимости от статуса тестов.
* **Запрет на «эхо-галлюцинации»**: запрещено выворачивать предостережения и требования пользователя в «дефекты существующего кода». Любая заявленная проблема в коде обязана подтверждаться реальными строками ([файл:строки]). Запрещено приписывать системе несуществующие баги.
* **Разделение прямых запросов пользователя и сторонних аудитов (ChatGPT и др.)**:
  - Пользователь часто консультируется со сторонними нейросетями (например, ChatGPT) и присылает их ответы или аудит в чат для сверки.
  - **Ответ сторонней нейросети НЕ является источником правды (Single Source of Truth) и НЕ является прямым руководством к действию**:
    - У сторонней нейросети нет полного доступа к кодовой базе репозитория, истории изменений и реальному окружению. Она склонна галлюцинировать, придумывать несуществующие дефекты или предлагать решения, несовместимые с архитектурой проекта.
  - **Правило критической верификации**:
    - Категорически запрещено слепо доверять стороннему аудиту и сразу переписывать код без проверки.
    - Каждое замечание сторонней нейросети обязано адресно проверяться по реальным файлам на диске (`working tree`), кодовой базе и тестам:
      - Если проблема подтверждается реальным кодом — зафиксировать это с цитатой ([файл:строки]) и учесть в плане.
      - Если замечание ошибочно или основано на галлюцинации — аргументированно опровергнуть его с доказательствами из кода.
  - **Разделение намерений**:
    - Прямые указания пользователя («сделай X», «исправь Y») — это требования задачи.
    - Пересылаемый пользователем аудит или ответ ChatGPT — это внешняя гипотеза для проверки, требующая строгой валидации по коду.
* **Инструменты разработки**: Antigravity 2 (Gemini) — основная среда, OpenCode — вспомогательная.

## Архитектурные принципы биллинга и простоты систем

* **Суть биллинга**: бот обеспечивает покупку и продление сетевого доступа. Это сервис подписок, а не клиринговый банк или биржа.
* **Принципы простоты**:
  - **Прямой пайплайн**: генерация ссылки на оплату выполняется напрямую через API платежного шлюза без создания избыточных промежуточных очередей в БД.
  - **Прозрачный учет и начисление**: понятная и предсказуемая логика добавления доступа пользователю без биржевых котировок, секундных дроблений и скрытых клиринговых списаний. Конкретный алгоритм расчета определяется актуальной продуктовой логикой тарифа и не сковывается жестким хардкодом в правилах.
  - **Ручные возвраты**: инициация банковских возвратов выполняется владельцем вручную через личный кабинет платежного шлюза с 2FA. Бот только принимает вебхук об успешном возврате (`refund.succeeded`) и отключает доступ.
* **Целевая 3-слойная модель биллинга**:
  1. **Платежные шлюзы (Адаптеры)**: изолированные провайдеры (`YooKassa`, `Telegram Stars`, `CryptoBot`) за единым интерфейсом (`create_payment_url`, `parse_webhook`). Замена или добавление шлюза не затрагивает логику подписок.
  2. **Заказы (Orders / Purchases)**: одна прозрачная запись факта покупки (кто, какой тариф/услугу, сколько рублей, метод оплаты, статус).
  3. **Прямая выдача (Fulfillment)**: успешная оплата -> продление доступа -> обновление ключа/конфигурации на целевом сервере.
* **Баланс и безопасность денег**:
  - Деньги пользователей неприкосновенны. Баланс ведется через прозрачные append-only транзакции кошелька (`account_ledger_entries`), исключающие потерю истории и случайные списания. Тарифы имеют фиксированные и предсказуемые цены.

## Telegram, интерфейс и Compliance

* **Ориентация на РФ и граница комплаенса**:
  - Вся клиентская база находится в РФ, сервис подключен к официальному российскому эквайрингу (ЮKassa / СБП).
  - **Внешний контур (Строгий комплаенс)**: всё, что доступно конечным пользователям и внешним проверяющим (модераторы эквайринга, банки, проверяющие органы, экраны бота, чеки, описания тарифов, публичные уведомления) — **категорически запрещено** использовать слова: `VPN`, `ВПН`, `обход блокировок`, `белые списки`, `глушилки`, `LTE`. Используется нейтральная профессиональная лексика: «сетевой доступ», «туннель», «защищенный протокол», «быстрый протокол», «подписка», «узел».
  - **Внутренний контур (Инженерная свобода)**: в кодовой базе, системных конфигах нод (Xray, AWG), служебных логах, тестах и технических параметрах админки искусственная цензура не требуется; используются точные технические термины протоколов.
* **Принципы Telegram-интерфейса**:
  - Архитектура Hub/Menu: минимум сообщений, закрываемые уведомления («Прочитано», «Закрыть»), в каждом экране есть возврат в главное меню, без тупиковых сценариев.
  - Административный интерфейс (`/admin`): компактный, информативный и удобный для управления проектом со смартфона (просмотр пользователей, продление, управление серверами, финансовая сводка) без необходимости заходить на сервер через консоль ради базовых операций.

## Протоколы подписок

### Стандартная подписка
* Только AmneziaWG: `awg` / `amneziawg`. Чистый WireGuard (`wg`) не поддерживается.
* Клиенты: `AmneziaVPN`, `AmneziaWG`, `DEFAULTVPN`. Поддержка `incy` планируется позже (когда появится стабильная поддержка AWG).

### Белый Интернет
* Только Xray VLESS over XHTTP через Yandex Cloud CDN (`docs/WL/WHITELIST_MASTER_GUIDE.md`).
* Клиенты: строго `incy`, остальные клиенты не поддерживаются.
* Формат выдачи: строго subscription URL (`sub`). Сырые ключи не поддерживаются.

### Разделение контуров
AmneziaWG и Xray строго изолированы:
* `AmneziaClient` обслуживает только AmneziaWG.
* `XrayNodeClient` обслуживает только Xray.
* Серверные пулы не смешиваются. Запросы к серверам фильтруются по `Server.protocol`.

## Безопасность и уровни риска

Запрещено логировать и коммитить токены, пароли, приватные ключи, API keys, cookies и ПДн.

Уровни риска:
* HIGH: платежи, баланс, подписки, БД/миграции, транзакции, конкурентность, авторизация, ключи, жизненный цикл серверов и продакшен.
* MEDIUM: воркеры, очереди, внешние API, хэндлеры, middleware, кэш.
* LOW: тексты, верстка UI, документация, форматирование.

При пересечении уровней действует наивысший.

## Приоритет источников и запрет устаревших знаний

1. Текущий рабочий контекст задачи (актуальные файлы на диске `working tree`, текущая ветка, прямые указания пользователя).
2. Состояние `origin/main` как стабильный baseline для слияния, безопасности продакшена и предотвращения регрессий.
3. Установленные версии зависимостей.
4. **Актуальная официальная документация (проверенная на текущую дату через web search / browser)**.
5. `docs/main_source.txt` и внутренние материалы проекта.
6. Актуальные проверенные внешние источники (неофициальные помечать маркером `UNOFFICIAL`).
7. Сторонние аудиты и ответы нейросетей (ChatGPT, Claude и др.), пересылаемые пользователем: рассматриваются строго как гипотезы для проверки (маркер `HYPOTHESIS`), а не как источник истины. Требуют обязательной проверки по реальному коду репозитория.
8. **Категорический запрет на спор с пользователем и абсолютный запрет выдавать внутреннюю память модели за источник истины**:
   - Внутренние веса и память модели содержат устаревшие знания о внешних API (особенно Telegram Bot API, aiogram, Xray-core, AmneziaWG, платёжные шлюзы).
   - Категорически запрещено спорить с пользователем и заявлять «в Telegram API этого нет», «это работает иначе» или навязывать устаревшие сигнатуры методов, опираясь на внутреннюю память.
   - Память модели имеет САМЫЙ НИЗКИЙ приоритет. Любое сомнение, параметр или утверждение о внешнем API обязаны проверяться на актуальную дату через официальную документацию (web search / browser) либо приниматься как факт от пользователя. Если пользователь говорит, что API работает так — верить пользователю и проверять актуальные доки.

## Среда и тестирование

* **Прагматичный контроль тестов и CI/CD (Risk-Based Testing)**:
  - **HIGH / MEDIUM (логика, код, БД, платежи, инфраструктура ноды, API)**: полный обязательный прогон тестов и 100% ожидание зелёного статуса GitHub Actions. Сдавать задачу без зелёного CI запрещено. При этом зелёный статус рассматривается строго как дополнительный автоматический барьер, а не как доказательство безупречности логики.
  - **LOW — Пользовательские тексты и экраны бота**: если PR меняет тексты UI, кнопки или сообщения для клиентов, обязателен только быстрый локальный аудит стоп-слов (`pytest tests/test_user_text_audit.py`). Гонять тяжёлые сьюты и блокирующе ждать длинные очереди CI для простой правки текста опечатки не требуется.
  - **DOCS / CHORE (документация, README, правила, комментарии, форматирование)**: достаточно проверки компиляции / линтера (`ruff check` / `python -m compileall`). Запуск тяжелых интеграционных тестов и долгое ожидание CI для таких правок избыточны и не тратят время владельца.
* **Разделение сред**:
  * **На Windows разрешено и обязательно**: статический анализ (`ruff check`), компиляция (`python -m compileall -q`), аудит стоп-слов (`pytest tests/test_user_text_audit.py`), быстрые изолированные модульные юнит-тесты без БД, без внешних процессов и без запуска bash-скриптов (`pytest tests/test_<module>.py`).
  * **На Windows категорически запрещено**: запускать тесты bash-скриптов (включая тесты нод, перенесённые в репозиторий `just1knode`), так как они запускают bash-подпроцессы в не-POSIX среде, зависают и вызывают блокировку терминала; запускать тяжёлые интеграционные сьюты с базами данных, параллельные прогоны и фоновые процессы (приводит к утечкам памяти и зависанию ПК).
  * **Тяжёлые проверки, тесты bash-скриптов нод и интеграционные тесты**: запускать в Ubuntu 24.04 через Docker Desktop или делегировать в GitHub Actions CI/CD (`test-node`, `test`, `docker-smoke-test`).
* **Стандарт эффективности и диагностичности тестов (Anti-Test Bloat & Regression Shield)**:
  - **Приоритет надежности и диагностичности**: главная цель теста — точная защита от регрессий (Regression Shield). Падение теста должно давать мгновенно понятную причину: один сломанный контракт — один упавший `assert` с однозначным контекстом. Запрещено жертвовать диагностичностью или полнотой проверок (`assert_not_called`, `assert_awaited_once`) ради формального сокращения строк.
  - **Запрет на бессмысленное раздувание (Anti-Bloat)**: не создавать пустые методы-клоны с идентичной структурой ради «накрутки» числа тестов. Близкие вариации данных объединять компактно, сохраняя независимость и информативность проверок.
  - **Запрет на тесты с искусственными задержками**: категорически запрещено использовать `time.sleep()` или длинные `asyncio.sleep()` — использовать моки, Fake/Stub объекты или виртуальное время.
  - **Бережное отношение к ресурсам CI**: юнит-тесты должны быть максимально быстрыми, изолированными и не зависеть от внешних сервисов, не замедляя общий прогон CI.
* Обязательно удалять за собой временные и мусорные dev-файлы (отладочные скрипты, scratch-файлы, дампы, логи). Не оставлять мусор в репозитории и working tree.

## Форматирование файлов и публикация на GitHub

* Кодировка: UTF-8 без BOM.
* Переводы строк: LF (`\n`).
* Пути к файлам: строго UNIX-слеши (`/`). Запрещено использовать обратные слеши (`\`), так как они интерпретируются как escape-последовательности (`\b` — backspace, `\n` — newline, `\t` — tab, `\a` — bell, `\f` — form feed).
* Markdown: имена файлов, пути и идентификаторы выделяются строго бэктиками (`` `symbol` ``), а НЕ обратными слешами (`\symbol\`).
* Создание и редактирование PR (`gh pr create`, `gh pr edit`):
  * **Обязательная фиксация задачи пользователя**: в самом начале описания PR первым разделом обязательно указывать исходный запрос или суть задачи пользователя (`## Исходная задача / User Request`), чтобы ревьюер сразу понимал контекст и требования.
  * Описание PR передавать СТРОГО через файл (`--body-file <file>`). Категорически запрещено передавать многострочный Markdown через аргумент `--body "..."` в PowerShell/Bash (интерполяция оболочки неизбежно искажает кавычки, экранирование и кодировку).
  * После создания/обновления PR временный файл удаляется.
  * Обязательно проверять отсутствие повреждённых управляющих символов (mojibake, control characters) в описании PR.
