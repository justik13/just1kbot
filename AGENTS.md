# just1kbot: Project Rules

## 1. Архитектура двух репозиториев

Проект разделен на два отдельных репозитория на GitHub:
* **`justik13/just1kbot`**: Telegram-бот, база данных (PostgreSQL, Alembic), биллинг (ЮKassa, Telegram Stars, CryptoBot), интерфейс пользователя и админка `/admin`, Docker Compose. Задачи ведутся PR-ами в этот репозиторий.
* **`justik13/just1knode`**: инфраструктура серверных узлов — CLI `just1knode`, модули Origin/Relay/Dual, сервисы Xray и Amnezia API, Nginx, UFW, gRPC, диагностика `just1knode doctor`. Задачи ведутся PR-ами в этот репозиторий.

Правила взаимодействия:
* Правки кода не смешиваются. Запрещено коммитить файлы ноды в репозиторий бота и наоборот.
* Репозитории связаны через сетевой API ноды (порт 8444). Изменения API ноды обязаны сохранять обратную совместимость с клиентами бота (`services/xray_node_client.py`, `services/amnezia_client.py`).
* Скрипт `scripts/just1knode.sh` в боте скачивает ветку `main` репозитория ноды. Ломающие изменения в `main` ноды недопустимы.

## 2. Контекст, масштаб и стек

* **Суть проекта**: коммерческий Telegram-сервис сетевых туннелей для клиентов из РФ под единоличным управлением владельца.
* **Администрирование**: владелец управляет проектом один, архитектура допускает подключение доверенного администратора поддержки (`ADMIN_IDS`). Админка `/admin` в Telegram — основной инструмент оперативного управления с телефона.
* **Масштаб**: целевой ориентир — до 100 активных пользователей в ближайшее время, до 1 000 пользователей в среднесрочной перспективе.
* **Стек**: монолит (aiogram 3, FastAPI, PostgreSQL, Docker Compose). Тяжелые брокеры очередей (Kafka, RabbitMQ, Celery) избыточны и не используются.
* **Принцип качества**: надежность важнее скорости. Любая проблема в кодовой базе подтверждается файлом и строкой (`[файл:строки]`). Придумывать несуществующие баги запрещено.
* **Зеленые тесты не являются доказательством безошибочности**: автотесты проверяют только то, на что написан `assert`. Зеленый статус тестов и проверок CI — это базовый автоматический фильтр явных поломок, а не гарантия идеальной работы в проде. Агент обязан анализировать логику, инварианты и пограничные сценарии независимо от статуса тестов.
* **Сторонние аудиты**: ответы ChatGPT, Claude и других моделей считаются гипотезами (`HYPOTHESIS`) и обязательно проверяются по реальным файлам репозитория.

## 3. Комплаенс и терминология

Клиенты сервиса находятся в РФ, платежи принимаются через ЮKassa и СБП. Действует строгое разделение контуров:
* **Внешний контур** (все экраны бота, кнопки, чеки, описания тарифов, уведомления, а также то, что видят модераторы эквайринга и банковские аудиторы):
  * Запрещены слова: `VPN`, `ВПН`, `обход блокировок`, `белые списки`, `глушилки`, `LTE`.
  * Используется нейтральная лексика: «сетевой доступ», «туннель», «защищенный протокол», «быстрый протокол», «подписка», «узел».
* **Внутренний контур** (исходный код, системные конфиги Xray и AmneziaWG, тесты, внутренние логи): действует стандартная инженерная терминология без цензуры.

## 4. Биллинг

* Бот продает и продлевает сетевой доступ. Это сервис подписок, а не клиринговый банк или биржа.
* **Прямой пайплайн**: платежная ссылка генерируется прямым вызовом API шлюза без создания промежуточных фоновых очередей и outbox-таблиц в БД.
* **Простой учет**: оплаченный период добавляется к активной подписке или от текущего момента (`max(now, end) + duration`). Запрещены любые многослойные схемы с учетом ценности в секундах, котировками промежуточных цен, резервированием долей баланса и синтетическим клирингом.
* **Возвраты**: выполняются владельцем вручную в кабинете платежного шлюза с 2FA. Бот только принимает вебхук `refund.succeeded` и отключает доступ.
* **Баланс**: история операций хранится в append-only таблице `account_ledger_entries`.

## 5. Сетевые протоколы

* **Стандартный доступ**: только AmneziaWG (`awg`). Клиенты: `AmneziaVPN`, `AmneziaWG`. Обычный WireGuard (`wg`) не поддерживается.
* **Белый Интернет**: только Xray VLESS over XHTTP через Yandex Cloud CDN. Клиент: строго `incy`. Формат выдачи: subscription URL (`sub`).
* Контуры AmneziaWG и Xray изолированы: клиенты `AmneziaClient` и `XrayNodeClient` не пересекаются, пулы серверов разделены по `Server.protocol`.

## 6. Продакшен и релизы

* Продакшен VPS изолированы, прямого доступа у агента нет. Все действия выполняет владелец.
* Ветка `main` — стабильная база релизов. Прямые коммиты в `main` запрещены, работа идет через PR.
* PR мерджит только владелец.
* **Штатное обслуживание — строго через CLI**:
  * Обновление бота: `just1kbot update`.
  * Обновление ноды: `just1knode update`.
  * Ручные правки файлов, конфигов, ручные перезапуски Docker и команды `iptables`/`sysctl` на проде запрещены (исключение — аварийный hotfix с детальным объяснением причин).
* **Проверки продакшена**:
  * **Pre-flight (ДО обновления)**: адресная read-only команда под скоуп текущего PR. Для базы данных — однострочник psql в контейнер `db` с выводом OK/FAIL. Для ноды — bash-проверка готовности окружения (порты, файлы) с выводом OK/FAIL. Для правок только текста или документации pre-flight не требуется. Запрещены бессмысленные команды вроде `SELECT count(*)`.
  * **Post-check (ПОСЛЕ обновления)**: для нод — запуск штатного инструмента `just1knode doctor`; для бота — `docker compose ps` и логи.

## 7. Среда разработки и тестирование

* **Разделение сред**:
  * На Windows разрешено: статический анализ (`ruff check`), компиляция (`python -m compileall -q .`), аудит стоп-слов (`pytest tests/test_user_text_audit.py`), быстрые юнит-тесты без БД.
  * На Windows запрещено: запускать bash-тесты ноды и тяжелые интеграционные сьюты с БД напрямую в ОС (вызывает зависания процессов).
  * Системные проверки и тесты bash-модулей ноды запускаются в Docker (Ubuntu) или делегируются в GitHub Actions CI.
* **Стандарт тестов**:
  * Тест обязан проверять реальный инвариант. Запрещены методы-клоны ради количества тестов.
  * Запрещены искусственные задержки (`time.sleep`).
* **Риск-ориентированный контроль CI/CD**:
  * Изменения кода, логики, БД, платежей, инфраструктуры нод: полный прогон тестов и обязательное ожидание зеленого статуса GitHub Actions. Сдавать задачу с красным CI запрещено.
  * Изменения пользовательских текстов: обязателен быстрый локальный аудит стоп-слов (`pytest tests/test_user_text_audit.py`).
  * Изменения документации, комментариев и правил: достаточно линтера `ruff check` и компиляции без блокирующего ожидания тяжелого CI.
* Мусорные и временные dev-файлы удаляются сразу после работы.

## 8. Приоритет источников и память модели

1. Рабочий контекст: актуальные файлы на диске (`working tree`), текущая ветка, указания пользователя.
2. Состояние `origin/main` как baseline релизов.
3. Актуальная официальная документация на текущую дату (web search / browser).
4. `docs/main_source.txt` и внутренние материалы проекта.
5. Сторонние аудиты (ChatGPT) — статус `HYPOTHESIS`, требуют проверки по коду.
6. **Память модели имеет самый низкий приоритет**: веса содержат устаревшие сведения о внешних API (особенно Telegram Bot API, aiogram, Xray, AmneziaWG, ЮKassa). Спорить с пользователем запрещено. Любое расхождение проверяется по свежей документации либо принимается от пользователя.
