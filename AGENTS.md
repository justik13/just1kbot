# just1kbot: Project Rules

## Production и Git

* GitHub `main`: стабильная production-база (Production Baseline) и эталон релизов.
* Продакшен изолирован: ветка `main` развёрнута на удалённых production VPS и обслуживает реальных пользователей. Прямого доступа (SSH/сеть) к production-инфраструктуре у агента нет.
* Production обновляется владельцем вручную через `just1kbot` для бота и `just1knode` для нод.
* **Штатное обслуживание и обновления — строго через CLI (`just1kbot` / `just1knode`)**:
  - Все регламентные действия, обслуживание и обновления на продакшене происходят **исключительно** через штатные утилиты: `just1kbot` (для бота) и `just1knode` (для нод).
  - Все обновления накатываются исключительно через штатные команды: `just1kbot update` для бота и `just1knode update` для нод.
  - Категорически запрещены ручные низкоуровневые команды (ручная правка файлов, правка конфигов, ручные `iptables`/`sysctl`/`docker` в обход CLI) при штатном обслуживании и релизах.
  - **Исключение — аварийные ситуации (Hotfix & Rollback)**:
    - Ручные команды на продакшене допускаются **только и исключительно** в случаях, если что-то сломалось и требуется экстренный hotfix для быстрого восстановления продакшена, либо для аварийного отката (rollback).
    - При возникновении такой ситуации агент обязан **предельно чётко и прозрачно пояснить**:
      1. Какую конкретно проблему мы решаем.
      2. Что именно делает предлагаемая команда и почему необходима именно она.
      3. Ожидаемый результат и как проверить успешность выполнения.
* Любое изменение, попадающее в `main`, должно быть проверено, соответствовать требованиям проекта и быть готово к безопасному production deployment без риска сбоев.
* **Стандарт Pre-flight и пост-диагностики продакшена (Строгая контекстность и Анти-«для галочки»)**:
  - Продакшен полностью изолирован, любые команды владелец выполняет вручную. Деструктивные команды на проде категорически запрещены.
  - **Категорический запрет на команды вне контекста (Strict Context Relevancy)**: любые диагностические или проверочные команды обязаны строго соответствовать контексту вносимых изменений:
    - Если PR отключает пинг (ICMP echo) или меняет сетевые параметры ядра/ноды — проверочные команды даются **строго для ноды** (например, проверка sysctl `sysctl net.ipv4.icmp_echo_ignore_all`, `just1knode doctor`, внешняя проверка пинга).
    - Pre-flight диагностика БД (через `psql`) требуется **ТОЛЬКО тогда, когда PR реально затрагивает базу данных, миграции, модели данных, биллинг или финансовые транзакции**. Категорически запрещено генерировать бессмысленные SQL-запросы к БД для PR, которые меняют только bash-скрипты нод (`just1knode`), системные утилиты, инфраструктурные конфиги, тексты UI, линтеры или тесты. Для чисто инфраструктурных задач pre-flight выдаётся либо по прямому контексту инфраструктуры (проверка синтаксиса `bash -n`, порты `ss`), либо не выдаётся вовсе, если обновление штатно выполняется через `just1knode update` / `just1kbot update`.
  - **Категорический запрет на метрики тщеславия (Vanity Metrics)**: запрещено выдавать бессмысленные `SELECT count(*) FROM table`, простые подсчеты строк или информационные дампы без условий. Факт наличия строк в БД ничего не говорит о совместимости с новым кодом.
  - **Принцип проверки граничных условий риска (Targeted Invariant Assertions)**: если PR затрагивает БД, проверка обязана формироваться строго на основе дифа текущего PR и проверять гипотезы сбоя (Failure Modes). Если PR меняет формулу квоты, тип поля, статус заказа, логику начисления бонусов или списания — SQL-запрос ОБЯЗАН адресно искать аномалии и строки, нарушающие эти новые инварианты (`WHERE <hazard_condition>`).
  - **Единый автономный канал выполнения БД-проверок**: запрещено полагаться на запуск Python-скриптов через контейнер бота (`docker compose exec bot python ...`), так как запуск через `exec` часто обходит точку входа (`docker-entrypoint.sh`), наследует некорректный `DATABASE_URL` (`localhost` вместо имени сервиса `db`) и приводит к сетевым сбоям (`Errno 111`). Все проверки БД обязаны оформляться **строго одной самодостаточной командой через psql напрямую в контейнер базы**:
    `docker compose exec -T db psql -U just1kbot -d just1kbot_bot -x -c "..."`
  - **Структура Pre-flight команды БД (включать ТОЛЬКО релевантные текущему PR блоки)**:
    1. *Миграции* (только если в PR есть миграция или меняется схема): проверка точного совпадения текущего `alembic_version` с ожидаемым head (вердикт `OK` / `FAIL: MISMATCH`).
    2. *Инварианты PR* (только если PR меняет бизнес-правила данных): поиск строк, нарушающих новые ограничения (`WHERE <hazard_condition>`, вердикт `OK (0 violations)` / `CRITICAL: HAS VIOLATIONS`).
    3. *Целостность финансов и балансов* (только при изменениях в биллинге/кошельках): проверка отсутствия отрицательных балансов и рассинхрона (вердикт `OK` / `CRITICAL`).
    4. *In-flight операции* (только при риске разрыва активных оплат перезапуском контейнеров или Cold Deploy): проверка отсутствия незавершённых заказов (`orders.status = 'pending'`, созданных за последние 15–30 минут, вердикт `OK (clean)` / `WARN: IN-FLIGHT ORDERS`).
       *Запрещено проверять `webhook_inbox.status = 'pending'`*: воркер, который переводил записи в `succeeded`, удалён в PR #277, поэтому в production пишутся только два статуса — `pending` и `succeeded`. Строки `pending` накапливаются и никогда не разбираются, из-за чего такая проверка всегда даёт ложное срабатывание.
* `main` напрямую не изменяется. Все изменения проходят через PR.
* PR мерджит только владелец проекта. Агенту мерджить запрещено.
* PR считается готовым к ревью только тогда, когда ВСЕ проверки GitHub Actions CI/CD успешно пройдены (зелёный статус). Сдавать работу с упавшим или незавершённым CI/CD категорически запрещено.
* Разделение Production Baseline и Рабочего контекста: `origin/main` — это целевая база для PR. Текущая работа ведётся в локальной рабочей ветке (`HEAD`) и с реальным состоянием файлов на диске (`working tree`), включая несохранённые/незакоммиченные правки пользователя. Запрещено игнорировать локальные файлы пользователя или спорить о том, что их «нет в main». Если пользователь сообщил, что изменил файлы локально или в другой ветке — агент обязан проверить диск и ветки репозитория.

## Контекст проекта

* Закрытый коммерческий проект одного владельца (Sole CEO/Admin).
* Разработка и поддержка ведутся через ИИ-агентов.
* Основная рабочая среда: Antigravity 2 (Gemini), вспомогательная: OpenCode.
* Код должен быть прагматичным: без оверинжиниринга, лишних абстракций и решений «на будущее», но и без чрезмерного упрощения.
* **Принцип качества и двойной проверки (Качество > Скорость)**: Лучше сделать глубокую двойную работу и перепроверить реализацию дважды, чем сделать поверхностно и быстро ради галочки. Скорость не является приоритетом. Любое утверждение, зависимость и краевой случай должны быть перепроверены по реальному коду и актуальным источникам. Запрещено срезать углы ради быстрого отчёта.
* **Запрет на «эхо-галлюцинации»**: запрещено выворачивать предостережения и требования пользователя в «дефекты существующего кода». Любая заявленная проблема в коде обязана подтверждаться реальными строками ([файл:строки]). Запрещено приписывать системе несуществующие баги.
* **Разделение прямых запросов пользователя и сторонних аудитов (ChatGPT и др.)**:
  - Пользователь часто консультируется со сторонними нейросетями (например, ChatGPT) и присылает их ответы или аудит в чат для сверки.
  - **Ответ сторонней нейросети НЕ является источником правды (Single Source of Truth) и НЕ является прямым руководством к действию**:
    - У сторонней нейросети нет полного доступа к кодовой базе репозитория, истории изменений и реальному окружению. Она склонна галлюцинировать, придумывать несуществующие дефекты или предлагать решения, несовместимые с архитектурой проекта.
  - **Правило критической верификации**:
    - Категорически запрещено слепо доверять стороннему аудиту и сразу переписывать код без проверки.
    - Каждое замечание сторонней нейросети обязано адресно проверяться по реальным файлам на диске (`working tree`), кодовой базе и тестам:
      - Если проблема подтверждается реальным кодом — зафиксировать это с цитатой ([файл:строки]) и учесть в плане.
      - Если замечание ошибочно или основано на галлюцинации — аргументированно опровергнуть его с доказательствами из кода.
  - **Разделение намерений**:
    - Прямые указания пользователя («сделай X», «исправь Y») — это требования задачи.
    - Пересылаемый пользователем аудит или ответ ChatGPT — это внешняя гипотеза для проверки, требующая строгой валидации по коду.

## Архитектурный принцип биллинга (Урок PR #275 и #276)

* **Суть проекта**: бот — это сервис подписок на туннели для пользователей, а НЕ коммерческий банк и НЕ клиринговая биржа.
* **Категорический запрет на банковский оверинжиниринг**:
  - Запрещено создавать многослойный учет ценности подписки в секундах (`paid_value_ledger`, `subscription_balance_service`), биржевые котировки с тайм-аутами (`tariff_quotes`), сложные клиринговые блокировки и аллокации (`account_balance_reservations`).
  - Запрещено встраивать инициацию банковских возвратов в Telegram-бота с очередями retries и outbox-воркерами. Владелец делает возврат вручную в личном кабинете платежного шлюза (ЮKassa) с 2FA, а бот только **принимает входящий вебхук** `refund.succeeded` и отключает доступ.
  - Запрещено создавать outbox-очереди создания платежей в БД (`payment_provider_operations` + воркер): создание ссылки на оплату через API шлюза выполняется напрямую в хэндлере за доли секунды.
* **Целевая 3-слойная модель биллинга**:
  1. **Платежные шлюзы (Адаптеры)**: изолированные провайдеры (`YooKassa`, `CryptoBot`, `Telegram Stars`) за единым интерфейсом (`create_payment_url`, `parse_webhook`). Замена или добавление шлюза не затрагивает логику подписок.
  2. **Заказы (Orders / Purchases)**: одна понятная запись факта покупки (кто, какой тариф/услугу, сколько рублей, метод оплаты, статус).
  3. **Прямая выдача (Fulfillment)**: подтверждена оплата -> продлили дату окончания подписки (`subscription_end = max(now, subscription_end) + duration_days`) -> обновили ключ на сервере.
* **Баланс и безопасность денег**:
  - Деньги пользователей неприкосновенны. Баланс ведется через прозрачные append-only транзакции кошелька (`account_ledger_entries`), исключающие потерю истории и случайные списания. Тарифы имеют фиксированные цены.

## Telegram и Compliance

* Telegram-интерфейс строится по принципу Hub/Menu: минимум сообщений, закрываемые уведомления («Прочитано», «Закрыть»), в каждом экране есть возврат в главное меню, без тупиковых сценариев.
* В пользовательских текстах, кнопках, чеках, тарифах и UI категорически запрещены слова: `VPN`, `ВПН`, `обход блокировок`, `белые списки`, `глушилки`, `LTE`.
* Причина: внутренний комплаенс проекта, законодательство РФ и защита эквайринга (ЮKassa) от блокировок. В техническом коде и внутренних комментариях использование термина допустимо.

## Протоколы подписок

### Стандартная подписка
* Только AmneziaWG: `awg` / `amneziawg`. Чистый WireGuard (`wg`) не поддерживается.
* Клиенты: `AmneziaVPN`, `AmneziaWG`, `DEFAULTVPN`. Поддержка `incy` планируется позже (когда появится стабильная поддержка AWG).

### Белый Интернет
* Только Xray VLESS over XHTTP через Yandex Cloud CDN (`docs/WL/WHITELIST_MASTER_GUIDE.md`).
* Клиенты: строго `incy`, остальные клиенты не поддерживаются.
* Формат выдачи: строго subscription URL (`sub`). Сырые ключи не поддерживаются.

### Разделение контуров
AmneziaWG и Xray строго изолированы:
* `AmneziaClient` обслуживает только AmneziaWG.
* `XrayNodeClient` обслуживает только Xray.
* Серверные пулы не смешиваются. Запросы к серверам фильтруются по `Server.protocol`.

## Безопасность и уровни риска

Запрещено логировать и коммитить токены, пароли, приватные ключи, API keys, cookies и ПДн.

Уровни риска:
* HIGH: платежи, баланс, подписки, БД/миграции, транзакции, конкурентность, авторизация, ключи, жизненный цикл серверов и продакшен.
* MEDIUM: воркеры, очереди, внешние API, хэндлеры, middleware, кэш.
* LOW: тексты, верстка UI, документация, форматирование.

При пересечении уровней действует наивысший.

## Приоритет источников

1. Текущий рабочий контекст задачи (актуальные файлы на диске `working tree`, текущая ветка, прямые указания пользователя).
2. Состояние `origin/main` как стабильный baseline для слияния, безопасности продакшена и предотвращения регрессий.
3. Установленные версии зависимостей.
4. Актуальная официальная документация (проверенная на текущую дату через web search / browser).
5. `docs/main_source.txt` и внутренние материалы проекта.
6. Актуальные проверенные внешние источники (неофициальные помечать маркером `UNOFFICIAL`).
7. Сторонние аудиты и ответы нейросетей (ChatGPT, Claude и др.), пересылаемые пользователем: рассматриваются строго как гипотезы для проверки (маркер `HYPOTHESIS`), а не как источник истины. Требуют обязательной проверки по реальному коду репозитория.

## Среда и тестирование

* Любой новый функционал или багфикс ОБЯЗАН покрываться реальными тестами. Запрещено отчитываться о выполнении без подтверждённого успешного прогона тестов.
* Разделение сред:
  * **На Windows разрешено и обязательно**: статический анализ (`ruff check`), компиляция (`python -m compileall -q`), аудит стоп-слов (`pytest tests/test_user_text_audit.py`), быстрые изолированные модульные юнит-тесты без БД, без внешних процессов и без запуска bash-скриптов (`pytest tests/test_<module>.py`).
  * **На Windows категорически запрещено**: запускать тесты bash-скриптов (`tests/test_just1knode_sh.py`), так как они запускают bash-подпроцессы в не-POSIX среде, зависают и вызывают блокировку терминала; запускать тяжёлые интеграционные сьюты с базами данных, параллельные прогоны и фоновые процессы (приводит к утечкам памяти и зависанию ПК).
  * **Тяжёлые проверки, тесты bash-скриптов нод и интеграционные тесты**: запускать в Ubuntu 24.04 через Docker Desktop или делегировать в GitHub Actions CI/CD (`test-node`, `test`, `docker-smoke-test`).
* **Стандарт эффективности и диагностичности тестов (Anti-Test Bloat & Regression Shield)**:
  - **Приоритет надежности и диагностичности**: главная цель теста — точная защита от регрессий (Regression Shield). Падение теста должно давать мгновенно понятную причину: один сломанный контракт — один упавший `assert` с однозначным контекстом. Запрещено жертвовать диагностичностью или полнотой проверок (`assert_not_called`, `assert_awaited_once`) ради формального сокращения строк.
  - **Запрет на бессмысленное раздувание (Anti-Bloat)**: не создавать пустые методы-клоны с идентичной структурой ради «накрутки» числа тестов. Близкие вариации данных объединять компактно, сохраняя независимость и информативность проверок.
  - **Запрет на тесты с искусственными задержками**: категорически запрещено использовать `time.sleep()` или длинные `asyncio.sleep()` — использовать моки, Fake/Stub объекты или виртуальное время.
  - **Бережное отношение к ресурсам CI**: юнит-тесты должны быть максимально быстрыми, изолированными и не зависеть от внешних сервисов, не замедляя общий прогон CI.
* GitHub Actions CI/CD:
  * Прогон воркфлоу в GitHub Actions является строго обязательным этапом контроля качества для каждого PR.
  * Агент обязан дождаться завершения всех проверок через `gh pr checks --watch` или `gh run watch`.
  * Успешный зелёный CI/CD обязателен для сдачи задачи, но не отменяет ответственности за корректность бизнес-логики.
* Обязательно удалять за собой временные и мусорные dev-файлы (отладочные скрипты, scratch-файлы, дампы, логи). Не оставлять мусор в репозитории и working tree.

## Форматирование файлов и публикация на GitHub

* Кодировка: UTF-8 без BOM.
* Переводы строк: LF (`\n`).
* Пути к файлам: строго UNIX-слеши (`/`). Запрещено использовать обратные слеши (`\`), так как они интерпретируются как escape-последовательности (`\b` — backspace, `\n` — newline, `\t` — tab, `\a` — bell, `\f` — form feed).
* Markdown: имена файлов, пути и идентификаторы выделяются строго бэктиками (`` `symbol` ``), а НЕ обратными слешами (`\symbol\`).
* Создание и редактирование PR (`gh pr create`, `gh pr edit`):
  * **Обязательная фиксация задачи пользователя**: в самом начале описания PR первым разделом обязательно указывать исходный запрос или суть задачи пользователя (`## Исходная задача / User Request`), чтобы ревьюер сразу понимал контекст и требования.
  * Описание PR передавать СТРОГО через файл (`--body-file <file>`). Категорически запрещено передавать многострочный Markdown через аргумент `--body "..."` в PowerShell/Bash (интерполяция оболочки неизбежно искажает кавычки, экранирование и кодировку).
  * После создания/обновления PR временный файл удаляется.
  * Обязательно проверять отсутствие повреждённых управляющих символов (mojibake, control characters) в описании PR.
